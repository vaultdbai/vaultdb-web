Unified Runner Interfaces - Implementation Summary

Overview

Successfully implemented a unified interface across all three runner implementations (Celery, AWS Batch, and AWS Lambda) while maintaining Celery scheduler compatibility for all runners.

📊 Test Results

All tests pass successfully! The implementation maintains backward compatibility while providing a unified interface across all three runners (Celery, AWS Batch, AWS Lambda).

Scheduler Implementation

1. Redis-backed Celery Beat Scheduler

File: src/vaultdb/scheduler/celery_beat.py

  • Implements RedisScheduler inheriting from celery.beat.Scheduler
  • Uses Redis for distributed locking (leader election) to ensure only one instance runs
  • Persists schedule state to Redis (ElastiCache)
  • Automatically discovers tasks from *_tasks.py files

2. AWS EventBridge Scheduler

File: src/vaultdb/scheduler/aws_deploy.py

  • Implements deploy_schedules to sync Celery schedules to AWS EventBridge
  • Converts Celery crontab and timedelta schedules to AWS cron() and rate() expressions
  • Clears existing vaultdb- prefixed rules before creating new ones
  • Configures rules to target the compute Lambda function

3. Task Discovery

File: src/vaultdb/scheduler/discovery.py

  • Implements discover_tasks to walk the package directory
  • Generic implementation supporting multiple packages, custom patterns, and exclusions
  • Imports *_tasks.py modules to register tasks with the Celery app

4. Celery Worker Entry Point

File: src/vaultdb/celery/worker.py

  • Initializes Celery app and performs task discovery
  • Exposes app object for Celery worker process
  • Ensures all tasks are registered before worker starts

5. Celery App Singleton

File: src/vaultdb/celery/celery.py

  • Implemented singleton pattern for setup_celery
  • Ensures all calls return the same Celery app instance
  • Critical for task registration during discovery process

6. Scheduler Startup

File: src/vaultdb/scheduler/beat.py

  • Entry point for Redis-backed Celery Beat scheduler
  • Initializes app, discovers tasks, and starts RedisScheduler programmatically

7. Service Scripts

Files: scripts/start_worker.sh, scripts/start_scheduler.sh

  • Bash scripts to easily start the worker and scheduler services
  • Sets up PYTHONPATH correctly
  • Uses the appropriate entry points (vaultdb.celery.worker and vaultdb.scheduler.beat)

8. Web API Enhancements

File: src/vaultdb/web/api.py

  • Updated FastAPI application to use lifespan events for startup
  • Integrated discover_tasks() to ensure all tasks are listed and available via API
  • Verified endpoints for listing tasks (GET /tasks) and submitting tasks (POST /tasks/submit)
  • Supports submitting tasks to different runners (Celery, Batch, Lambda) via runner parameter

Interface Consistency

All three runners now share the following common interface:

class Runner:
    task_cls: str  # Path to task class

    def send_task(name, args, kwargs, **options) -> AsyncResult:
        """Send task for execution"""
        pass

    def AsyncResult(task_id, **kwargs) -> AsyncResult:
        """Get async result for task"""
        pass

    @property
    def tasks(self):
        """Task registry"""
        pass

Task Class Consistency

All task classes (Task, BatchTask, LambdaTask) now have:

  • Scheduler attributes: queue, routing_key, exchange, priority
  • _extract_routing() method for routing information
  • _get_exec_options() method for execution options
  • TaskStatus lifecycle hooks from BaseTask

Celery Scheduler Integration

All runners can now be used with Celery scheduler because:

  1. All task classes have routing/queue attributes
  2. All task classes implement _extract_routing() method
  3. Task execution options include scheduler-compatible parameters
  4. Runners can be invoked through Celery's message broker

Backward Compatibility

The changes maintain backward compatibility:

  • setup_celery() still returns an object with task() decorator method
  • Existing Celery tasks continue to work
  • Task classes retain all previous functionality
  • Only addition is the unified interface, no removals

Known Issues/Notes

  1. Lambda Module Name: The lambda directory uses a Python reserved keyword. This was addressed by using importlib for dynamic imports.

  2. PYTHONPATH Requirement: The devcontainer now sets PYTHONPATH to /vaultdb/src to ensure proper module resolution.

  3. Celery Dependency: The Celery module requires the celery package to be installed. This is already in requirements.txt.
