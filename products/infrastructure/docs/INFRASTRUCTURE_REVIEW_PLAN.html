VaultDB Infrastructure Review & Remediation Plan

In-depth review of infrastructure/cloudformation/. Because this stack is distributed for "one-click" customer deployment and is the target for the core End-to-End test plan (core/docs/E2E_TESTING_STRATEGY.md, phases P3/P4/P5), it must (a) actually deploy, (b) run the workflow engine, and (c) meet least-privilege / cost / ops bars.

Last reviewed: 2026-05-16, against a live audit of all 13 templates, the master-stack wiring, and the core runtime contracts they must satisfy.

How to read this

Two classes of issue, deliberately separated:

  • Section 1 — Deploy & Runtime Blockers (Phase 0). The stack does not deploy as scripted, and even if forced through, the workflow subsystem is non-functional. These must be fixed before any E2E phase or hardening work. None of these were in the previous version of this plan.
  • Sections 2–4 — Hardening (Phases 1–3). Security, cost, and ops improvements. The previous plan's content, validated and corrected for three technical hazards that would have broken the stack if executed as originally written.

Severity: 🔴 CRITICAL (blocks workflow) · 🟠 HIGH (blocks deploy) · 🟡 MEDIUM · 🟢 LOW.

Section 1 — Deploy & Runtime Blockers (Phase 0)

1.1 🔴 Workflow approval HMAC secret is provisioned nowhere

Evidence. core/src/vaultdb/approval/key_store.py resolves the approval signing key in this order: 1. APPROVAL_SECRETS_ARN → a Secrets Manager secret whose JSON must be exactly {"current_version": N, "keys": {"1": "<hex>", ...}} (hex = 32 random bytes, 64 hex chars), or 2. env APPROVAL_SECRET_CURRENT + APPROVAL_SECRET_V{n}, or 3. legacy APPROVAL_SECRET / WORKFLOW_APPROVAL_SECRET. If none resolve → RuntimeError: No approval key configured.

ops-secrets-manager.yaml's unified secret has only 8 keys (supervisor_*, auth_client_*, redis_auth, cognito_client_secret, vaultdb_*). ecs-service.yaml injects 8 matching env vars. No approval key anywhere; no APPROVAL_SECRETS_ARN injected into ECS / Lambda / Batch.

Impact. submit_workflow / execute_workflow (the triple-gate — the headline BMA-compliance feature) raise on first call in every deployed environment. Blocks E2E phases P2 C-WF.*, P3, P5 workflow cases entirely.

Fix. - Add a dedicated AWS::SecretsManager::Secret (do not reuse the unified secret — key_store._load_from_secrets_manager does json.loads and requires the exact {"current_version","keys"} shape; the unified blob's shape would crash it). - Shape: {"current_version": 1, "keys": {"1": "<64-hex>"}}. - Operator supplies the 32-byte key as a NoEcho parameter (openssl rand -hex 32), consistent with how SupervisorPassword is handled. No default (forces a real value at deploy, like SupervisorPassword). - Export ${ProjectName}-${Environment}-approval-secret-arn. - Inject env APPROVAL_SECRETS_ARN (the ARN, not the value — the app fetches it via boto3) into ecs-service, lambda-function, and batch-environments task/job definitions (workflows can execute on any runner). - ✅ No IAM change needed in P0. iam-roles.yaml already grants secretsmanager:GetSecretValue + DescribeSecret on arn:…:secret:${ProjectName}-${Environment}-*, which already covers a secret named ${ProjectName}-${Environment}-approval-secret. Tightening that wildcard is the Section 2.1 hardening job, not P0. - ⚠️ LambdaStack and BatchStack must gain - SecretsStack in their DependsOn. They are currently unconditional and do not depend on SecretsStack; importing approval-secret-arn without the dependency races stack creation → intermittent deploy failure ("No export named …-approval-secret-arn"). ECSStack.DependsOn already includes SecretsStack (OK). SecretsStack itself is unconditional, so the export is always present for the unconditional Lambda/Batch consumers — only the ordering needs fixing.

Files: ops-secrets-manager.yaml, master-stack.yaml, ecs-service.yaml, lambda-function.yaml, batch-environments.yaml.

1.2 🟠 Stack does not deploy as scripted

Evidence. master-stack.yaml has no-default parameters: VpcId, PublicSubnet1Id, PublicSubnet2Id, PrivateSubnet1Id, PrivateSubnet2Id, SupervisorPassword (plus TemplatesBucketName). core/scripts/deploy_infra.sh passes only ProjectName, Environment, TemplatesBucketName, AdminEmail, DemoUserEmail → CloudFormation rejects: "Parameters: [VpcId, …] must have values." infrastructure/CLAUDE.md documents --parameter-overrides file://params-dev.json, but no params-*.json exists in the repo.

Impact. P5 (and any real deploy) cannot start.

Fix. - Add infrastructure/cloudformation/params-dev.json.example enumerating every required parameter, with inline guidance (incl. the openssl rand -hex 32 command for 1.1's key). - Update core/scripts/deploy_infra.sh to consume a params file (and fail fast with a clear message if VPC/subnet/secret params are absent). - Keep secrets out of any committed file — .example only, real params-dev.json git-ignored.

Files: infrastructure/cloudformation/params-dev.json.example (new), core/scripts/deploy_infra.sh.

1.3 🟡 OIDC provider URLs never reach the app

Evidence (corrected during implementation). The original assumption was "export the Cognito OAuth URLs." That is wrong: cognito-auth.yaml is a placeholder — it provisions only a Cognito Identity Pool (OIDC→AWS credential bridge); it has no User Pool, and its UserPoolId / OAuth2AuthorizeUrl / OAuth2TokenUrl / HostedUIUrl outputs are literally the string 'N/A'. The real OIDC provider is external (Google/GitHub/etc. — see the AuthClientId param description "OAuth2 Client ID (Google, GitHub, etc.)"). So there is nothing real on Cognito to export; the app simply never gets its IdP endpoint URLs (only the client id/secret).

Impact. OIDC login (E2E P6 manual UI) cannot complete end-to-end.

Fix (corrected). Treat the IdP URLs as operator configuration, not Cognito-derived: - Add params AuthAuthorizationUrl, AuthTokenUrl, AuthUserinfoUrl to master-stack.yaml (defaults may mirror core's Google defaults) and pass them to ECSStack. - In ecs-service.yaml set env AUTH_AUTHORIZATION_URL, AUTH_TOKEN_URL, AUTH_USERINFO_URL from those params, and derive AUTH_REDIRECT_URI as http://${alb-dns}/auth/callback via the existing ${ProjectName}-${Environment}-alb-dns export (ECSStack already DependsOn LoadBalancerStack). Env names verified against core config._ENV_MAP: AUTH_AUTHORIZATION_URL, AUTH_TOKEN_URL, AUTH_USERINFO_URL, AUTH_REDIRECT_URI. - No cognito-auth.yaml change and no new ECSStack → CognitoStack dependency (the original plan's step here was based on the wrong premise).

Files: master-stack.yaml, ecs-service.yaml.

1.4 🟡 Bring-Your-Own-VPC prerequisite is undocumented

The stack consumes an existing VPC + 2 public + 2 private subnets; it does not create them. Nothing in the deploy script, README, or the E2E plan states this. Document it as a hard prerequisite alongside 1.2's params file.

Files: infrastructure/README.md (prereqs section), params example.

1.4.5 🟢 No-admin deploys (scoped deploy role + bootstrap) — IMPLEMENTED

The deploy path no longer requires account-admin credentials. A one-time bootstrap (admin) creates two scoped IAM roles; every deploy after that uses them and needs no admin.

  • bootstrap-deploy-role.yaml (new) creates:
  • ${Project}-${Env}-cfn-exec-role — CloudFormation assumes this to create/update/delete the stack. Scoped to the ${Project}-${Env}-* namespace (S3, Secrets, IAM roles/policies/ instance-profiles all by-prefix), with explicit hard-denies on privilege escalation (iam:CreateUser, iam:CreateAccessKey, iam:UpdateAssumeRolePolicy, iam:*PolicyVersion, organizations:*, account:*). NOT admin.
  • ${Project}-${Env}-deployer-role — operator/CI assumes this before deploying. Permissions: cloudformation:* on the project's stack ARN, iam:PassRole (constrained to cloudformation.amazonaws.com), and s3:* on the templates bucket. No resource-creation rights of its own.

  • ${Project}-${Env}-app-boundary — permissions boundary exported (${Project}-${Env}-app-boundary-arn) for iam-roles.yaml to attach to every runtime role in P1 hardening; hard-caps what any app role can ever do regardless of its own policy.

  • core/scripts/bootstrap_deploy_role.sh (new) — admin runs once per environment: bash core/scripts/bootstrap_deploy_role.sh <project> <env> <region> <deployer-arn>. Prints the two role ARNs.

  • core/scripts/deploy_infra.sh (updated) — if DEPLOYER_ROLE_ARN is set it sts:assume-role's into it (drops admin); if DEPLOY_ROLE_ARN is set it passes --role-arn to cloudformation deploy so CFN itself runs as the scoped exec role. Falls back to caller creds if neither is set (back-compat), with a warning.

Deploy flow (least-privilege):

admin    : bootstrap_deploy_role.sh    # once, ever, creates the 2 roles
operator : export DEPLOYER_ROLE_ARN=…  # from bootstrap output
operator : export DEPLOY_ROLE_ARN=…    # from bootstrap output
operator : deploy_infra.sh             # NO admin needed

What this does NOT change: the vaultdb-auth (OIDC → Cognito → S3) self-serve path for analysts is unchanged and remains the right tool for P4 data-plane E2E. The bootstrap is the only step that needs admin, and only the first time.

Helpers: - core/scripts/assume_deployer.sh — eval-able exports so you can run ad-hoc aws ... commands as the deployer role from your IAM-user shell. - core/scripts/teardown_infra.sh — see 1.4.6 below.

1.4.6 🟢 Teardown & cost discipline — IMPLEMENTED

The stack has hourly-billed resources even when ECS Fargate is scaled to 0. After every test session, run teardown to stop the bill.

Resource Bills when idle? Order-of-magnitude (us-east-1)
ElastiCache Redis YES ~$0.017/hr/node (cache.t3.micro) — biggest sleeper
Application LB YES ~$0.022/hr + per-LCU
EFS YES (small) ~$0.30/GB-month (commitlog files only)
NAT Gateway YES ~$0.045/hr + $0.045/GB processed
ECS Fargate tasks only if Min>0 default MinCapacity=0 → free idle
Batch / Lambda only on run Spot-priced; idle = 0
S3 / ECR storage pennies persistent — fine to leave

core/scripts/teardown_infra.sh does, in order: 1. Assumes the deployer role (same flow as deploy_infra.sh — no admin). 2. Explicitly empties versioned project S3 buckets ({project}-{env}-data) via list-object-versions + delete-objects — does NOT trust the stack's S3CleanupLambda (per §4 it can fail silently). 3. cloudformation delete-stack + wait stack-delete-complete. 4. Optional flags: - --delete-templates-bucket — also delete the CFN-templates bucket. - --teardown-bootstrap — also delete the bootstrap stack (the deployer + cfn-exec roles themselves; needs admin because iam:DeleteRole on those role ARNs is outside the deployer-role's own grant). 5. Refuses to run on prod (prod's data bucket has DeletionPolicy: Retain anyway — controlled change-management only).

Recommended discipline for E2E P5: deploy → drive test cases → bash core/scripts/teardown_infra.sh vaultdb dev us-east-1 before walking away. Leaving the stack up overnight on dev ≈ Redis + ALB + EFS + NAT continuously billing for nothing.

1.5 🟢 ALB is HTTP-only (no 443 / ACM)

load-balancer.yaml opens 80/5555/8888 to 0.0.0.0/0 with no TLS listener. Acceptable for E2E; must not ship to prod. Note here so the hardening track (Section 2) treats transport encryption consistently with its KMS ask (2.4).

1.6 🔴 Lambda handler & run_type broken — FIXED

Found while reviewing the container path: - Dockerfile.lambda CMD ["vaultdb.lambda.handler.task_handler"] and docker/scripts/entrypoint.sh python -m vaultdb.lambda.handler — no vaultdb.lambda module exists (lambda is a Python keyword; module is vaultdb.function.handler, callable task_handler). Every Lambda cold-start failed → FUNCTION runner 100% broken in AWS. - Dockerfile.lambda set ENV run_type=lambda. config.run_type is now env-mapped (_ENV_MAP), and RunType only accepts service|function|batch|local — lambda is invalid. - Fixed: Dockerfile.lambda → run_type=function + CMD ["vaultdb.function.handler.task_handler"]; entrypoint.sh → vaultdb.function.handler (and stale start_fastapi fallback vaultdb.web.app:app → vaultdb.web:app).

1.7 🟠 Deployed images install from PyPI, not local source

Dockerfile.{service,lambda,batch-*} run pip install vaultdb.core (PyPI). E2E phases that use these images test the published package, not the working tree. To validate local core changes, rebuild images from a local wheel/source. Tracked as the "artifact-under-test" rule in core/docs/E2E_TESTING_STRATEGY.md §0.

1.8 🔴 Flower (monitor) is internet-exposed with no auth

service/scripts/start-monitor.sh: MONITOR_BASIC_AUTH defaults empty → Flower starts with no authentication. load-balancer.yaml publishes port 5555 to 0.0.0.0/0 (monitor target group). Anyone on the internet can enumerate tasks (args may contain sensitive data) and revoke / terminate them. core ships vaultdb/service/flower_auth.py (OAuth-protected) which this script does not use.

Fix. Refuse to start Flower unauthenticated in any deployed env: wire flower_auth (OAuth) or require a non-empty MONITOR_BASIC_AUTH; and remove 5555 from the public ALB (internal-only, or behind ALB auth/OIDC). Files: start-monitor.sh, load-balancer.yaml.

1.9 🔴 Jupyter auth disabled on Environment=dev (the deploy default)

service/scripts/start-jupyter.sh: when ENVIRONMENT∈{dev,local} with no token/password it sets --NotebookApp.token='' --NotebookApp.password=''. master-stack.yaml defaults Environment=dev, and the ALB publishes 8888 to 0.0.0.0/0. With ENABLE_JUPYTER=true on a default deploy this is unauthenticated Jupyter (RCE) open to the internet. Compounding bug: array elements like "--NotebookApp.token='${JUPYTER_TOKEN}'" keep the literal single quotes, so token/empty handling is broken and unpredictable regardless of environment.

Fix. Never key auth off dev; require a token/password in every deployed env (fail closed if absent); remove the literal quotes; drop --NotebookApp.allow_origin='*'; do not ALB-expose 8888 publicly; reconsider shipping Jupyter in a production image at all. Files: start-jupyter.sh, load-balancer.yaml, Dockerfile.service.

1.10 🔴 Batch & Lambda images lack the KRONOS domain modules

Dockerfile.service installs vaultdb.{assumptions,liability,scenario,alm,trading,valuation,risk,reporting,ingestion}. Dockerfile.batch-cpu/.gpu/.lambda install only vaultdb.core. Workflow steps / TED tasks dispatch domain tasks (e.g. valuation.tasks.run), so any Batch or Lambda job running an actuarial task fails with ModuleNotFoundError. The BATCH/FUNCTION service types can run core test tasks but not the workloads they exist for — breaks E2E P5 and real prod batch/lambda.

Fix. Install the domain-module set in the batch/lambda images (or a shared base image). Files: Dockerfile.batch-cpu, Dockerfile.batch-gpu, Dockerfile.lambda.

1.11 🟠 Celery Beat has no single-instance / leader guard

[program:service-beat] runs in every ECS replica; the service autoscales 0→N. With ENABLE_BEAT=true and >1 task, every scheduled job fires once per replica (N× duplicate execution). No leader election.

Status — RESOLVED (Option B implemented). Uses RedBeat (celery-redbeat): the schedule lives in Redis and RedBeat holds a distributed lock so exactly one Beat instance is the active scheduler at a time, with automatic failover. Beat may run in every autoscaled replica — no MaxCapacity=1 pinning required.

Changes: - Dockerfile.service: pip install … celery-redbeat. - start-beat.sh: --scheduler=redbeat.RedBeatScheduler; dropped the file-based --schedule and the singleton contract. RedBeat connects to the Celery broker Redis (broker_url == SERVICE_BROKER_URL) — no core change needed. - supervisord.conf [program:service-beat] unchanged (still gated by ENABLE_BEAT); it is now safe under autoscaling.

Decision rationale: Option B chosen over A (no extra ECS task; one fewer service to size/deploy); RedBeat is the standard Celery solution and handles failover natively.

Section 2 — Security Hardening (validated + corrected)

The previous plan's security items are valid and retained. Three carried a hidden hazard that would have broken the stack if executed verbatim — corrected below.

2.1 IAM Resource: '*' over-permissioning — VALID

iam-roles.yaml Batch/ECS/ECR statements use Resource: '*'.

⚠️ Correction to the original fix. The original plan said "pass ECSClusterArn / BatchQueueArn / ECRRepoArns as parameters into iam-roles.yaml." This inverts the dependency graph — S3Stack, BatchStack, ECSStack all DependsOn IAMRolesStack; making IAM consume their ARNs creates a circular nested-stack dependency that will not deploy. Correct approach: scope by ARN pattern using !Sub on the already-deterministic names, e.g. arn:aws:ecr:${AWS::Region}:${AWS::AccountId}:repository/${ProjectName}-${Environment}-*, arn:aws:batch:${AWS::Region}:${AWS::AccountId}:job-queue/${ProjectName}-${Environment}-*. No cross-stack ARN passing, no cycle.

2.2 EFS access point runs as root 0:0 / 777 — VALID

vpc-networking.yaml EfsAccessPoint hardcodes Uid:0 Gid:0 and 777.

⚠️ Runtime-UID audit done — the images are inconsistent TODAY. All three mount the same EFS access point for the DuckLake .ducklake commitlog, but run as different users: - ECS service: supervisord (root) drops every program to user=service. Now pinned to uid/gid 1000 (Dockerfile.service useradd -u 1000) so it aligns with the proposed access-point uid. - Batch (Dockerfile.batch-cpu/.gpu): no USER → runs as root (uid 0). - Lambda: runs as the Lambda runtime sandbox user.

This is a pre-existing cross-runner corruption risk (root-owned vs 1000-owned files on shared EFS), independent of the hardening. The §2.2 fix is therefore not just "set the access point to 1000" — it must reconcile all three images to the same uid (1000): keep ECS as-is (done), add a matching non-root user to the Batch images (verify no batch job needs root first — GPU/driver paths), and confirm the Lambda EFS access-point uid. Apply the access-point 1000:1000/755 change only after all images agree, with a post-change /mnt/commitlog write test per runner.

2.3 S3 delete permission vs. immutable archive — VALID (clarified)

s3-bucket.yaml grants s3:DeleteObject bucket-wide to execution roles.

Clarifications: - This is the archive-bucket immutability concern (TODO #6) and is distinct from the approval signing key in 1.1 — the previous plan conflated them. 1.1 must be fixed regardless of any Object-Lock work here. - ⚠️ ObjectLockEnabled is creation-time only and requires bucket versioning; it cannot be retrofitted, and is impossible on the ExistingDataBucketName reuse path. The fix must therefore be: (a) deny s3:DeleteObject on approval-archive/ + production/ prefixes via bucket/role policy (works on existing buckets too), and (b) set ObjectLockEnabled: true only on the newly-created-bucket branch.

2.4 🟢 SSE-KMS option — VALID (optional)

Offer SSE-KMS as an opt-in parameter for cryptographic access auditing; keep AES256 default for cost. Pair with 1.5 (TLS) for a coherent encryption posture.

Section 3 — Cost: VPC Endpoints (VALID)

No S3 Gateway / ECR / Secrets Manager / Logs interface endpoints → all private-subnet egress traverses NAT (~$0.045/GB). With DuckLake Parquet + ML image pulls this becomes the top bill line. Add S3 Gateway endpoint (free) + ECR/Secrets/Logs interface endpoints.

⚠️ Note (BYO-VPC): because the VPC is customer-supplied (1.4), endpoint creation may collide with their existing routing/endpoints. Make the endpoint stack optional (a CreateVpcEndpoints condition, default true) so reuse scenarios can opt out.

Section 4 — Operational Reliability (VALID)

  • ECR imageScanningConfiguration: scanOnPush: true.
  • S3CleanupLambda custom resource: add a DLQ + bounded retry; it can fail silently on large buckets and wedge stack deletion.
  • Add alarms for RunningTaskCount = 0 and BatchQueueDepth high (stalled-processing detection); current alarms are CPU/Mem only.

4.1 Container hardening (MEDIUM, from docker/ review)

  • supervisord fail-closed-too-hard. supervisord.conf uses %(ENV_SUPERVISOR_USER)s / %(ENV_AUTH_CLIENT_ID)s etc. with no defaults — a single missing secret key makes supervisord FATAL at config parse (the whole container dies, no degraded mode). Provide safe defaults or validate required env in entrypoint.sh before exec'ing supervisord, with a clear error.
  • AWS_PROFILE=${DEPLOYMENT_ENV} anti-pattern. Points boto3 at a creds-less profile and pins region (production→us-west-2); only works because AWS_REGION env overrides and the task-role chain still resolves. In role-based ECS/Batch/Lambda, do not set AWS_PROFILE; rely on the container/task credential provider + AWS_REGION.
  • test-builds.sh. Counts the GPU build as FAILED then exit 1 even when NVIDIA-absent is expected (CI false negative); the Lambda image help/version checks are meaningless (Lambda RIC entrypoint, not entrypoint.sh). Make GPU optional/skipped; drop the Lambda help/version asserts.
  • Jupyter --NotebookApp.allow_origin='*' weakens origin/CSRF — tie to the §1.9 fix.

Section 5 — Cross-Stack Contract Audit (verified SOUND — no action)

Recorded so future readers know what was checked:

  • All 13 templates parse. Nested-stack orchestration is coherent.
  • Every Fn::ImportValue has a matching Export: under the consistent ${ProjectName}-${Environment}-<suffix> convention. Spot- verified: redis-endpoint/redis-port, all IAM role ARNs, VPC subnets/SGs, ECR URIs, S3 bucket name/arn, unified-secret-arn, ALB target-group ARNs. No dangling import found.
  • IAM export→import names are internally consistent across lambda/batch/ecs/s3/ops. s3-bucket.yaml intentionally wires the three runner role ARNs into the bucket policy.
  • master-stack DependsOn ordering respects every producer→consumer ImportValue requirement.
  • Endpoint exposure path is wired: ALB SG (80/5555/8888) → TGs (8000/5555/8888) → ECS registers via imported TG ARNs → LoadBalancerDNS output. Visible by design (modulo 1.5 TLS).
  • DuckLake env wiring present: CATALOG_DATA_PATH, commitlog_directory=/mnt/commitlog, Redis broker/result/cache URLs — all map to config._ENV_MAP.
