VaultDB Core Extraction Module Architecture

The vaultdb/extraction module orchestrates the process of extracting, interpreting, and structuring complex actuarial and financial data from raw documents (PDFs, HTML, TXT). Instead of simple regex or heuristics, it uses advanced LLM workflows combined with a tiered prompt architecture, schema validation, and intelligent document parsing.

Key Components

1. ExtractionAdvisor (advisor.py)

This is the core orchestrator. It extends BaseLLMAdvisor (from the crawler) and manages the full end-to-end extraction pipeline: - Token Budgeting: Assembles document text and table chunks so they fit precisely within the LLM's context window. - Prompt Execution: Merges the user/system prompts with document variables and executes the LLM calls. - Resilience: Implements retry logic and exponential backoff for robustness against LLM API timeouts or empty responses. - Dependency Flow: Exposes extract_batch() which topologically sorts prompts by their dependencies, feeding the output of upstream extractions (e.g., getting a "Product Catalog" first) into the variables of downstream prompts. - Backend Swapping: Dynamically chooses providers (Gemini, Anthropic, Ollama, Bedrock, etc.) based on the prompt's preferred_backend or fallback logic.

2. Document Parser (parsers.py)

Converts raw binaries and plain text into structured Document objects containing easily readable tables and chunked text. - PDF Parsing: Relies primarily on PyMuPDF (fitz) for layout-aware text extraction and table identification. - HTML Parsing: Leverages BeautifulSoup with rules specific to regulatory filings and corporate content. - Gracefully drops back to raw ASCII text scanning if optional dependencies aren't met, ensuring the pipeline never fully fails.

3. Prompt Registry (prompts.py)

Prompts are defined as first-class Python classes inheriting from BaseExtractionPrompt. They encompass standard components: - System and User prompts. - Tiers & Focus: - Tier 1: Product Structure (Catalogs, surrender schedules, indexing strategies). - Tier 2: Actuarial Assumptions (Lapse rates, mortality inferences). - Tier 3: Regulatory/Financial Data (SEC Summaries). - Target Filtering: Defines which file types/folders (e.g. ['FIA', 'VA']) to feed the prompt.

4. Schemas and Validation (schemas.py)

Because LLMs return wildly varying outputs, the engine strictly enforces structured JSON returns. - Validates structural soundness (required keys, nested dict shapes). - Outputs explicit warnings for data that fails to meet schema constraints without completely dropping the result, adhering to a "keep what is useful" philosophy.

5. Persistence (results.py and tasks.py)

  • Extraction results are saved to .json files.
  • If a prompt has produces_csv = True (e.g., surrender charge schedules or withdrawal tables), it dynamically flattens the JSON response and exports analytical .csv files ready for direct downstream use in actuarial models or DataFrame ingest.
  • Task wrappers (tasks.py) like extract_carrier expose async-ready entrypoints for the broader task engine (e.g. Celery).

High-Level Workflow

  1. A task starts for an insurance Carrier.
  2. Parser globs all relevant PDFs/HTML in the input directory and structures them into context-aware chunks.
  3. The Advisor collects the Prompt Registry's active prompts for that carrier/product type.
  4. Execution runs sequentially along the dependency graph (e.g., Tier 1 first, then Tier 2).
  5. For each prompt, the LLM processes the generated prompt alongside the document chunk, returning JSON.
  6. Schema Validation checks the JSON.
  7. Results are persisted to directories matching prospectuses/docs/prospectuses/<carrier> with structured .json and flat .csv artifacts.

CLI Usage

The extraction module includes a fully functional CLI built in at vaultdb.extraction.cli. It is designed to run batch extractions, test single prompts computationally, and inspect module status seamlessly. Local models like ollama are the strict zero-config default.

# Run a specific extraction for a carrier using the default local provider (Ollama)
python -m vaultdb.extraction.cli carrier "Jackson_National"

# Test a single prompt using an explicit cloud provider (e.g. Gemini)
python -m vaultdb.extraction.cli single "Jackson_National" 1.3 --backend gemini --api-key "AIzaSy..."

# Explicitly override the input/output paths on the fly without relying on configurations
python -m vaultdb.extraction.cli carrier "Jackson_National" \
    --input-dir "d:\sandbox\jackson_raw_docs" \
    --output-dir "d:\sandbox\jackson_extracted_data"

Configuration

The Extraction module pulls parameters directly from the central vaultdb.config namespace. You can configure behavior dynamically on deployment using environment variables or by mapping them into vaultdb_config.py: - LLM_BACKEND -> c.llm_backend - PROSPECTUS_DIR -> c.prospectus_dir - EXTRACTION_OUTPUT_DIR -> c.extraction_output_dir - EXTRACTION_MAX_TOKENS_PER_CHUNK -> c.extraction_max_tokens_per_chunk
