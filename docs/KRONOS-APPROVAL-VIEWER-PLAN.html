KRONOS Re — Centralized Approval System & Skill-Based Visualization

Date: 2026-03-28 Status: Design / Pre-implementation Author: AI-drafted; human architect to review and approve Depends on: KRONOS-CHATBOT-PLAN.md, KRONOS-BUILD-PLAN.md

1. Problem Statement

1.1 What is missing today

The current workflow viewer is a small 4-column Cytoscape sidebar embedded in the chatbot page. It shows: - Node names and dependency edges - A tiny step detail card on click (task name, status, timeout, on_failure)

This is insufficient for a BMA-regulated Bermuda SPI reinsurer. Before an actuary or CIO approves a multi-step computational workflow, they need to see:

Needed Current
Full step kwargs (what inputs go into each task) Not shown
Data lineage (which step's output feeds which step's input) Not shown
Execution timeline (Gantt, step durations) Not shown
Raw JSON of the full workflow definition Not shown
Who is approving and their full identity on record Only OIDC sub captured
Approval details on record: email, display name, session, IP Not captured
Reusable approval UI for trades, reports, policy changes Not built
Skill-based visualizations (other teams extend the viewer) Not built

1.2 Goals

  1. Rich workflow viewer — a dedicated full-page viewer for any workflow run, with interactive DAG, step inspector, data flow, timeline, and raw JSON.
  2. Skill-based visualization — the workflow viewer is the first built-in skill. Other teams can ship GitHub skills that register additional visualizer types (e.g. BSCR chart, trading Greeks surface, mortality curve).
  3. Centralized approval service — one DuckLake-backed service in core that records approvals for any subject type (WORKFLOW, REPORT, TRADE, POLICY_CHANGE, etc.) with full user identity.
  4. Approval panel component — a reusable Dash component embedded by any skill's viewer page.

2. Centralized Approval System — core/src/vaultdb/approval/

2.1 Why move approval out of vaultdb.workflow

The current WorkflowApproval model only approves workflows. Within 6 months we will need:

Approval subject Trigger Approver role
WorkflowRun AI proposes steps Actuary / CIO
BSCR Report Period-end report generated Appointed Actuary
TradeRecommendation AI proposes hedge CIO
DataIngestionBatch Ceding carrier data uploaded Data Steward
AssumptionSet Mortality / lapse tables changed Appointed Actuary
PolicyCohort migration Block restructure CIO + Actuary

All share the same approval pattern: human reviews → approves → HMAC token created → downstream service verifies before acting.

2.3 HMAC token — full user identity embedded

Current token message (workflow only):

f"{workflow_id}:{approved_by}:{approved_at_iso}"

New token message (all subject types):

message = "|".join([
    approval_id,          # unique per approval
    subject_id,           # what is being approved
    subject_type,         # WORKFLOW / REPORT / TRADE / ...
    approver_id,          # OIDC sub
    approver_email,       # email at approval time
    approved_at_iso,      # UTC ISO timestamp
])
token = HMAC-SHA256(APPROVAL_SECRET, message)

Including approval_id makes each token unique even for the same subject+approver. Including approver_email ties the token to the specific person (not just sub).

2.4 Independent Policy Engine — core/src/vaultdb/approval/policy.py

Decision (2026-03-28): Policy enforcement is at the API level and is independent of the approval creation service.

"Independent" has two meanings here:

  1. Architecturally decoupled — service.py (create_approval) contains zero policy logic. It is a pure HMAC-generation + DB-write function. Policy enforcement happens in a dedicated PolicyEnforcer that sits between the HTTP request and the service call. Adding or removing a policy rule never touches service.py.

  2. Rule-level independence — each policy constraint (role check, notes check, min-review-time, no-self-approval, etc.) is a separate PolicyRule object. Rules are evaluated independently and their violations are aggregated. This means:

  3. Each rule is unit-testable in complete isolation.
  4. New rules are added by writing one class, not by editing a monolithic function.
  5. Rules are composable — a given ApprovalPolicy DB row activates a subset of rules.

Policy Engine structure

core/src/vaultdb/approval/
    __init__.py
    models.py          — ApprovalRecord, ApprovalPolicy (data only, no logic)
    service.py         — create_approval(), verify_approval(), revoke_approval(), get_audit_trail()

ApprovalContext — all data a rule needs

@dataclass
class ApprovalContext:
    subject_id: str
    subject_type: str
    subject_name: str
    approver_id: str
    approver_email: str
    approver_roles: list[str]       # OIDC roles at request time
    submitter_id: str | None        # who created/submitted the subject (e.g. who proposed the workflow)
    notes: str
    viewer_opened_at: datetime | None  # timestamp the viewer page was first loaded (from session cookie)
    request_time: datetime          # when the approval POST arrived
    ip_address: str
    session_id: str
    user_agent: str

viewer_opened_at is written to the session when the viewer page renders and read back at approval time — enabling MinReviewTimeRule without client-side trust.

PolicyRule ABC

@dataclass
class PolicyViolation:
    rule: str           # rule class name
    code: str           # machine-readable code e.g. "INSUFFICIENT_ROLE"
    message: str        # human-readable, shown in UI

class PolicyRule(ABC):
    """A single independently evaluable approval constraint."""

    @abstractmethod
    def check(
        self,
        policy: ApprovalPolicy,
        context: ApprovalContext,
    ) -> list[PolicyViolation]:
        """Return empty list if the rule passes, or one+ violations if it fails."""
        ...

Built-in rules (all independent, all individually testable)

Rule class ApprovalPolicy field that activates it What it checks
RequiredRolesRule required_approver_roles (non-empty) context.approver_roles must contain at least one required role
RequireNotesRule require_notes = True context.notes must be non-empty
MinReviewTimeRule min_review_seconds > 0 request_time - viewer_opened_at >= min_review_seconds
NoSelfApprovalRule no_self_approval = True approver_id != submitter_id
ExpiryRule expiry_hours > 0 Existing valid approval must be < expiry_hours old (prevents double-approval)
SingleApproverRule always active No existing non-revoked approval by this approver for this subject

PolicyEnforcer

class PolicyEnforcer:
    """Loads policy for a subject_type, evaluates all applicable rules, returns result."""

    _RULES: list[PolicyRule] = [
        RequiredRolesRule(),
        RequireNotesRule(),
        MinReviewTimeRule(),
        NoSelfApprovalRule(),
        ExpiryRule(),
        SingleApproverRule(),
    ]

    def enforce(
        self,
        context: ApprovalContext,
    ) -> PolicyEnforcementResult:
        policy = ApprovalPolicy.get(subject_type=context.subject_type)
        if policy is None:
            # No policy configured = allow (open policy)
            return PolicyEnforcementResult(passed=True, violations=[])

        all_violations: list[PolicyViolation] = []
        for rule in self._RULES:
            all_violations.extend(rule.check(policy, context))

        return PolicyEnforcementResult(
            passed=len(all_violations) == 0,
            violations=all_violations,
        )

How the API endpoint uses the enforcer

# dashboard/api/approvals.py

@router.post("/approvals")
async def create_approval_endpoint(
    req: ApprovalRequest,
    request: Request,
) -> ApprovalResponse:
    ctx = _build_context(req, request)           # extract from session + headers
    result = policy_enforcer.enforce(ctx)        # independent policy engine
    if not result.passed:
        raise HTTPException(
            status_code=403,
            detail={
                "error": "approval_policy_violation",
                "violations": [v.__dict__ for v in result.violations],
            },
        )
    # Policy passed — call pure service (no policy logic here)
    record = create_approval(**ctx.__dict__)
    return ApprovalResponse.from_record(record)

The UI reads the violations list and renders each message inline in the approval panel (e.g. "You do not have the Appointed Actuary role required to approve BSCR reports").

PolicyEnforcementResult

@dataclass
class PolicyEnforcementResult:
    passed: bool
    violations: list[PolicyViolation]

    @property
    def error_codes(self) -> list[str]:
        return [v.code for v in self.violations]

2.5 WorkflowApproval migration

WorkflowApproval in vaultdb.workflow.models is kept for backwards compatibility but its execute_workflow() gate is updated to also accept an ApprovalRecord with subject_type="WORKFLOW". Both records are written on approval — old and new — so existing code continues to work while new code uses the generic system.

Long-term: WorkflowApproval becomes a thin alias that queries ApprovalRecord(subject_type="WORKFLOW").

3.2 Skill Registry

# dashboard/skills/registry.py

class VisualizerRegistration:
    skill_name: str
    subject_type: str          # WORKFLOW / REPORT / TRADE / ...
    label: str                 # "Workflow Viewer"
    description: str
    build_layout: Callable     # (data: dict) -> Dash layout
    is_builtin: bool

class SkillRegistry:
    """Singleton registry for all visualization skills."""

    def register_visualizer(
        self,
        skill_name: str,
        subject_type: str,
        label: str,
        description: str,
        build_layout: Callable,
        is_builtin: bool = False,
    ) -> None: ...

    def get_visualizer(self, subject_type: str) -> VisualizerRegistration | None: ...
    def list_visualizers(self) -> list[VisualizerRegistration]: ...

SKILL_REGISTRY = SkillRegistry()

Built-in skills are registered at dashboard startup in dashboard/__init__.py (or server.py lifespan):

from dashboard.skills.workflow_viewer import register
register()  # registers WORKFLOW visualizer

User-installed GitHub skills can also register visualizers by including an entry point in their kronos-skill.toml:

[skill]
name = "bscr-chart-skill"
visualizer_subject_type = "REPORT"
visualizer_entry_point = "bscr_chart_skill.viewer:build_layout"

The skill_manager.py installer detects visualizer_subject_type and calls SKILL_REGISTRY.register_visualizer() after pip install.

3.3 How a new skill adds a visualizer (example)

A team ships github.com/kronos-re/skill-bscr-chart:

# kronos-skill.toml

4.2 Tab 1 — DAG View (dag_panel.py)

Cytoscape with dagre layout, enhanced:

  • Node content: step name (line 1) + task short name (line 2, muted)
  • Node size: scales with number of kwargs (complexity indicator)
  • Node color: by status (PENDING=grey, RUNNING=blue-pulse, DONE=green, FAILED=red, SKIPPED=amber)
  • Edge style: solid for hard dependencies, dashed for soft (on_failure=continue)
  • Edge label: the $step_xxx.result.field ref value when it exists (data flow annotation)
  • Hover tooltip: task full path, timeout, on_failure, depends_on count
  • Click: highlights node, populates Step Inspector panel below
  • Zoom controls: fit, zoom in/out, center
  • Legend: status color legend in corner

4.3 Tab 2 — Step List (step_list.py)

Dash dbc.Accordion with one item per step:

▶ step_001 — Project Cash Flows                        [DONE ✓]
  Task:       liability.tasks.project_cash_flows
  Depends on: (none)
  Inputs:     block_id=TED-FA-2026, n_periods=360, valuation_date=2026-03-31
  Output:     {run_id: "CF_001", rows: 12000, ...}      [copy]
  Timing:     Started 14:23:01 · Finished 14:24:47 · Duration 1m46s

Each accordion item is colour-coded by status. Clicking expands the full kwargs tree (rendered as a collapsible JSON tree) and the result JSON.

4.4 Tab 3 — Data Flow (data_flow.py)

A second Cytoscape graph that shows data lineage — specifically $step_xxx.result.field references:

  • Nodes: step outputs (as oval chips) and step inputs (as rectangular chips)
  • Edges: labelled with the field name being passed
  • Example: step_001.result.run_id → step_002.kwargs.run_id

This answers "where does each step's input come from?" — critical for auditors reviewing a workflow before approval.

4.5 Tab 4 — Timeline (timeline.py)

Plotly Gantt chart (only shown for RUNNING/DONE/FAILED runs):

  • X-axis: wall clock time
  • Y-axis: step name
  • Bar color: by status
  • Hover: duration, start time, end time, result summary

For PENDING_APPROVAL runs: shows estimated timeline based on step timeouts.

4.6 Tab 5 — JSON View (json_viewer.py)

Full workflow definition as pretty-printed JSON with: - Syntax highlighting via dcc.Markdown with a fenced json code block (rendered by Prism.js via Dash's assets) - "Copy to clipboard" button - "Download as .json" button (dcc.Download) - Schema validation badge: ✓ Valid / ✗ Invalid (runs validate_workflow_definition() inline)

5.2 API endpoint — POST /api/v1/kronos/approvals

New endpoint in dashboard/api/approvals.py:

POST /approvals                         — create approval
GET  /approvals/{approval_id}           — get one record
GET  /approvals?subject_id=&type=       — list/search approvals
POST /approvals/{approval_id}/revoke    — revoke
GET  /approvals/audit?subject_id=       — audit trail (PDF-printable view)

The POST /approvals endpoint: 1. Reads request.state.session for user_id, email, display_name, roles 2. Reads X-Forwarded-For for ip_address 3. Reads User-Agent header 4. Reads Dashboard-Session-ID cookie for session_id 5. Calls vaultdb.approval.service.create_approval(...) — creates ApprovalRecord 6. If subject_type == "WORKFLOW": also writes WorkflowApproval (backwards compat) 7. Returns approval details including token suffix and audit_id

6. Dedicated Workflow Viewer Page

6.1 Route and file

dashboard/pages/workflow_viewer.py URL: /workflow?id={workflow_id} Nav: accessible from: - Chatbot page "View details →" link in the proposed workflow card - Recent Workflows list "View" link - Dashboard home "Recent Runs" table "View" link

6.2 Data loading

On page load (dcc.Location callback): 1. Extract workflow_id from URL query string 2. GET /api/v1/kronos/chatbot/workflows/{workflow_id} 3. Render SKILL_REGISTRY.get_visualizer("WORKFLOW").build_layout(workflow_data) 4. Append ApprovalPanel(subject_id, subject_type="WORKFLOW", ...) at bottom

If workflow_id is missing: redirect to /chatbot.

6.3 Live updates

dcc.Interval (3s) polls workflow status while status == RUNNING: 1. Re-fetch workflow from API 2. Update DAG node colors, step inspector, timeline 3. Stop polling when status in {DONE, FAILED, REJECTED}

Chatbot page (dashboard/pages/chatbot.py) is simplified:

  • DAG panel remains in the sidebar for quick preview
  • Add "View full details →" link button below the DAG that navigates to /workflow?id={workflow_id}

10. Key Decisions Made

  1. ApprovalRecord is the canonical approval record. WorkflowApproval becomes a backwards-compat alias. All new code (trades, reports, policy changes) uses ApprovalRecord(subject_type=...).

  2. HMAC token now includes approver email. This ties the cryptographic proof to a specific named person, not just an opaque OIDC sub — required for BMA audit trail.

  3. Policy enforcement is at the API level and is independent of the approval service. service.py contains zero policy logic. PolicyEnforcer (in policy.py) is called by the API endpoint before create_approval(). Each PolicyRule is independently testable and composable. New rules are added by writing one class — nothing else changes.

  4. ApprovalContext carries all inputs a rule needs. Includes viewer_opened_at (server-side timestamp from session — client cannot forge it) enabling MinReviewTimeRule without trusting the client.

  5. Policy violations are structured JSON. Each violation has rule, code, and message. The UI renders messages inline in the approval panel. Callers can check code programmatically.

  6. Built-in skills live in dashboard/skills/. They are always available and registered at server startup. User-installed GitHub skills augment them by declaring visualizer_entry_point in kronos-skill.toml.

  7. One visualizer per subject type. The registry maps subject_type → visualizer. A GitHub skill can override the built-in visualizer for a given type, or register one for a new type.

  8. Dedicated viewer page at /workflow?id=. Full-page, not a modal — regulators and auditors need printable, full-resolution views. The page uses @media print CSS to produce a clean PDF.

  9. Minimum review time is server-enforced. viewer_opened_at is written to the server-side session when the viewer page renders. MinReviewTimeRule computes the delta on the server at approval time. The UI shows a countdown, but the rule cannot be bypassed by skipping the countdown.

  10. Approval audit trail is PDF-exportable. GET /approvals/audit?subject_id= returns a full HTML report (via ReportHTMLGenerator) with all approval records, timestamps, and token suffixes — suitable for regulatory submission.

13. Key Versioning for APPROVAL_SECRET

Decision (2026-03-28): Yes, key versioning is more secure. We will version the approval secret.

13.1 The problem without versioning

Without versioning, a secret rotation invalidates every existing HMAC token in the database. An approved workflow that has not yet executed becomes un-executable — the triple gate fails HMAC verification because the token was generated with the old key. This creates two bad options:

Option Problem
Rotate key → all existing approvals broken Actuary must re-approve everything manually. Operationally unacceptable.
Never rotate key Secret rotation is a standard security hygiene requirement. The key lives forever → increasing breach exposure.

Key versioning solves this: old tokens remain verifiable using the old key version, and new tokens use the current key.

13.2 Design — ApprovalKeyVersion

core/src/vaultdb/approval/
    key_store.py     — ApprovalKeyVersion model + KeyStore service

ApprovalKeyVersion model:

Field Type Description
key_version Integer PK Monotonically increasing (1, 2, 3, …)
key_id Text Short human-readable tag, e.g. "v1", "v2"
key_hint Text Last 8 chars of the key (for debugging, never the full key)
activated_at DateTime When this version became active
retired_at DateTime When this version stopped being used for new tokens (NULL = current)
is_current Boolean Only one row has True at any time
created_by Text OIDC sub of the admin who rotated

The key itself is NEVER stored in the database. Only the key_version integer is stored. The actual key bytes live in Secrets Manager (AWS) or the environment, namespaced by version:

APPROVAL_SECRET_V1=<bytes>
APPROVAL_SECRET_V2=<bytes>
APPROVAL_SECRET_V3=<bytes>   ← current
APPROVAL_SECRET_CURRENT=3    ← which version is active

Or as a single JSON structure in one Secrets Manager secret:

{
  "current_version": 3,
  "keys": {
    "1": "<hex-encoded-key-v1>",
    "2": "<hex-encoded-key-v2>",
    "3": "<hex-encoded-key-v3>"
  }
}

13.3 Updated HMAC token — version embedded

The token now includes the key version so verification knows which key to load:

token = f"v{key_version}:{hmac_hex}"

Example: "v3:a3f9c1e2b8d4..."

Token generation:

def _generate_token(message: str) -> tuple[str, int]:
    """Returns (versioned_token, key_version)."""
    version, key_bytes = KeyStore.get_current_key()
    mac = hmac.new(key_bytes, message.encode(), hashlib.sha256).hexdigest()
    return f"v{version}:{mac}", version

Token verification:

def _verify_token(token: str, message: str) -> bool:
    """Verify regardless of which key version was used."""
    if ":" not in token:
        return False
    version_tag, mac = token.split(":", 1)
    try:
        version = int(version_tag.lstrip("v"))
    except ValueError:
        return False
    key_bytes = KeyStore.get_key_version(version)
    if key_bytes is None:
        return False   # version unknown or deleted
    expected = hmac.new(key_bytes, message.encode(), hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, mac)

Field Type Description
key_version Integer Which key version generated this token
token Text Now stores "v{N}:{hmac_hex}" (backwards compat: old rows without v prefix use v1)

13.5 Key rotation procedure

Rotation is an admin operation (not user-triggered):

  1. Admin generates new key bytes out-of-band (e.g. openssl rand -hex 32).
  2. Admin pushes new key to Secrets Manager under version N+1.
  3. Admin calls POST /api/v1/kronos/admin/approvals/rotate-key — writes new ApprovalKeyVersion row (sets is_current=True, sets previous row's retired_at=now).
  4. From this point: all new ApprovalRecord tokens use v(N+1).
  5. All existing records with vN tokens remain verifiable because vN key is still in Secrets Manager.

Key deletion (optional, only after all vN records have been superseded):

  • Soft-delete: set ApprovalKeyVersion.is_deletable=True when all ApprovalRecord rows using that version have is_valid=False or have been executed.
  • Hard-delete: admin removes key bytes from Secrets Manager after confirming no live records use that version.

13.7 Why this is more secure than a single unversioned key

Property Single key Versioned keys
Secret rotation Breaks all existing tokens Old tokens verifiable, rotation safe
Breach impact Full re-approval of everything Only new approvals use the new key; old ones stay valid until executed
Auditability Cannot tell when a token was generated key_version in token reveals the key era
Gradual retirement Not possible Old key versions can be deleted once no live records use them
Replay attack mitigation None beyond HMAC approval_id in message makes each token unique; key rotation limits replay window

13.8 Updated ApprovalPolicy fields

Add token_expiry_hours (distinct from expiry_hours):

Field Description
token_expiry_hours HMAC token becomes invalid N hours after approved_at even if not revoked. 0 = never expires. ExpiryRule checks this.

This means a BSCR report approval that was given 3 months ago cannot be used to execute the same report today — the token has expired and a fresh approval is required.
