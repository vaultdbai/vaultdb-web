ChatHub — Architecture & Design

ChatHub is a JupyterHub-style process manager that spawns isolated per-user chatbot servers. It runs on port 8060 and is managed by supervisord as kronos-chathub.

Why Per-User Processes?

Each user gets their own FastAPI server (UserProcess) running on a unique port (9100-9999). This provides:

  1. Memory isolation — One user's conversation history cannot leak to another.
  2. Resource limits — CPU (600s), memory (2GB), file descriptors (256), processes (16) enforced per user via preexec_fn.
  3. Secret isolation — UserProcesses receive only allowlisted environment variables. Approval secrets, AWS keys, and database URLs are stripped.
  4. Fault isolation — A crashed UserProcess does not affect other users.

Security Model

Environment Isolation

When spawning a UserProcess, ChatHub strips the environment to an explicit allowlist:

Allowed (forwarded to child): - USER_ID, WORKSPACE_ROOT, PORT - ANTHROPIC_API_KEY - HUB_API_URL, HUB_INTERNAL_TOKEN - KRONOS_BLOCK_ID, VAULTDB_API_URL

Denied (never forwarded): - WORKFLOW_APPROVAL_SECRET / APPROVAL_SECRET_* - AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY - DATABASE_URL, REDIS_URL - AUTH_CLIENT_SECRET

This means the AI (running inside UserProcess) can never: - Forge approval tokens (no access to secrets) - Access the database directly (no connection string) - Impersonate AWS operations (no credentials)

Token Verification

Every request from ChatHub to a UserProcess includes an X-Hub-Token header containing an HMAC-SHA256 token:

token = hmac_sha256(HUB_INTERNAL_SECRET, f"{user_id}:{session_id}:{spawn_ts}")

The UserProcess verifies this token on every request. This prevents: - Direct access to UserProcess ports from outside ChatHub - Cross-user request forgery

Resource Limits

Applied via preexec_fn on the subprocess:

Resource Limit Purpose
CPU time 600 seconds Prevent runaway computation
Memory (RSS) 2 GB Prevent memory exhaustion
File descriptors 256 Prevent resource exhaustion
Processes 16 Prevent fork bombs

Hub Internal API

ChatHub exposes internal endpoints under /_hub/api/ for workflow operations:

Endpoint Method Purpose
/_hub/api/workflows/submit POST UserProcess submits AI-proposed workflow
/_hub/api/workflows/approve POST Dashboard records human approval
/_hub/api/workflows/{id}/execute POST Dashboard triggers workflow execution
/_hub/api/workflows GET List user's workflows
/_hub/api/workflows/{id} GET Get workflow with step details
/_hub/api/processes GET List active UserProcesses (admin)
/_hub/api/processes/{user_id} DELETE Kill a UserProcess
/_hub/api/healthz GET Liveness probe

UserProcess Endpoints

Each UserProcess (ports 9100-9999) exposes:

Endpoint Method Purpose
/healthz GET Liveness (polled by Hub at spawn)
/message POST Send user message, get AI reply
/history GET Get conversation history
/history DELETE Clear conversation
/skills GET List installed skills
/skills/install POST Install GitHub skill
/skills/{name} DELETE Uninstall skill
/workspace GET List workspace files

Idle Reaping

A background task runs every 60 seconds, checking last_active on each UserProcess. If a process has been idle for 30 minutes:

  1. Send SIGTERM (graceful shutdown).
  2. Wait 5 seconds.
  3. If still alive, send SIGKILL.
  4. Remove from process registry.
