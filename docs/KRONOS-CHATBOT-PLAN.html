KRONOS Re — AI Chatbot & Workflow Engine Plan

Date: 2026-03-28 Updated: 2026-03-28 — Process isolation model added (JupyterHub-style) Status: Design / Pre-implementation Author: AI-drafted; human architect to review and approve

1. Overview

Add an AI chatbot to the KRONOS Re dashboard, built on the Anthropic Claude SDK, that:

  1. Lets users converse naturally to build KRONOS Re workflows (valuation runs, ALM snapshots, risk computations, report generation)
  2. Supports a per-user plugin/skill system installed from GitHub
  3. Gives each user an isolated workspace folder and an isolated OS process — JupyterHub-style
  4. Renders the proposed workflow as a visual DAG for human review and approval
  5. On approval, serialises the workflow to structured JSON and submits it to a new WorkflowManager task in vaultdb.core
  6. WorkflowManager verifies approval in the database before executing any step — enforcing the BMA human-in-the-loop mandate

2. Process Isolation Model (JupyterHub-style)

2.1 Why process isolation

Running all users in the same process is a significant security risk:

Without isolation With process isolation
Any bug in user-installed skill can crash all users Crash is contained to one process
Skills can read os.environ and get AUTH_CLIENT_SECRET, ANTHROPIC_API_KEY, etc. Child process env is stripped and rebuilt from allowlist only
A skill can call os.listdir("/workspaces") and read other users' files CWD is set to user workspace; path traversal blocked at hub
One user's CPU-bound skill blocks all other users' LLM calls Each process has its own GIL, CPU limits, and async event loop
Memory leak in one session leaks across all sessions Process is recycled when session ends

2.3 Environment variable allowlist

The hub uses a strict allowlist when spawning each UserProcess. Nothing from the hub's own environment is inherited:

# dashboard/chatbot/hub.py

CHILD_ENV_ALLOWLIST = {
    # Mandatory — identity and workspace
    "USER_ID",
    "WORKSPACE_ROOT",       # set to workspaces/{user_id}/ — NOT the parent dir
    "PORT",

    # Anthropic SDK — read-only API key, no write side-effects
    "ANTHROPIC_API_KEY",

    # Internal hub API — per-spawn HMAC token, scoped to this user+session
    "HUB_API_URL",
    "HUB_INTERNAL_TOKEN",

    # KRONOS read API — read-only calls only; approval goes through hub
    "VAULTDB_API_URL",

    # Python runtime — minimal
    "PATH",
    "HOME",                 # set to workspaces/{user_id}/
    "PYTHONPATH",           # set to user's site-packages + module src dirs
    "LANG",
    "LC_ALL",
}

# The following NEVER appear in child env:
CHILD_ENV_DENY = {
    "WORKFLOW_APPROVAL_SECRET",  # cannot forge approval tokens
    "AUTH_CLIENT_ID",
    "AUTH_CLIENT_SECRET",
    "SERVICE_BROKER_URL",        # no direct Redis access
    "AWS_ACCESS_KEY_ID",
    "AWS_SECRET_ACCESS_KEY",
    "CATALOG_DATA_PATH",         # no direct DuckLake writes
    "commitlog_directory",
    "SUPERVISOR_USER",
    "SUPERVISOR_PASSWORD",
}

Hub: SIGTERM → UserProcess immediately
     status = STOPPED
     All workspace data persists (only process is killed, not files)

2.5 Resource limits per process

Applied in the child process immediately after fork() via preexec_fn:

import resource

def _child_resource_limits():
    """Called in child before exec — applies per-user resource caps."""
    # Max CPU time: 10 minutes per task (prevents infinite loops in skills)
    resource.setrlimit(resource.RLIMIT_CPU, (600, 600))
    # Max virtual memory: 2 GB (prevents memory-bomb skills)
    resource.setrlimit(resource.RLIMIT_AS, (2 * 1024**3, 2 * 1024**3))
    # Max open file descriptors: 256 (prevents fd exhaustion)
    resource.setrlimit(resource.RLIMIT_NOFILE, (256, 256))
    # Max child processes: 16 (prevents fork bomb in skills)
    resource.setrlimit(resource.RLIMIT_NPROC, (16, 16))
    # Disable core dumps
    resource.setrlimit(resource.RLIMIT_CORE, (0, 0))

2.6 Workspace path guard

The UserProcess enforces that all file operations stay within its assigned workspace:

# dashboard/chatbot/workspace.py  (runs inside UserProcess)

WORKSPACE_ROOT = Path(os.environ["WORKSPACE_ROOT"]).resolve()

def safe_path(relative: str) -> Path:
    """Resolve a user-supplied path and assert it stays inside workspace."""
    resolved = (WORKSPACE_ROOT / relative).resolve()
    if not str(resolved).startswith(str(WORKSPACE_ROOT)):
        raise PermissionError(f"Path traversal blocked: {relative!r}")
    return resolved

.. traversal, symlink attacks, and absolute paths supplied by user/Claude are all blocked here.

2.7 Hub internal token

Each spawned process gets a short-lived HMAC token scoped to (user_id, session_id). The hub verifies this on every /_hub/api/* call:

hub_token = HMAC-SHA256(
    key = HUB_INTERNAL_SECRET,         # never leaves the hub process
    msg = f"{user_id}:{session_id}:{spawn_timestamp}"
)
# expires after IDLE_TIMEOUT + 5 min

A UserProcess can only call hub API endpoints on behalf of its own user_id. It cannot impersonate another user or access another user's data through the hub proxy.

4.3 Conversation loop

User message
    │
    ▼
engine.chat(session_id, user_message)
    │
    ├─ Load conversation history from ConversationSession model
    ├─ Append user message
    ├─ Call Claude SDK (messages.create with tools)
    │
    ├─ If response contains tool_use blocks:
    │      ├─ Execute each tool (read-only KRONOS API calls, workspace ops)
    │      ├─ If tool = propose_workflow → save WorkflowRun(status=DRAFT) to DB
    │      └─ Append tool_result blocks, call Claude again
    │
    ├─ Extract final text response
    ├─ Persist updated history to ConversationSession
    └─ Return {assistant_text, proposed_workflow_id?}

5.2 Installation flow

User: "Install skill from https://github.com/acme/kronos-skill-stress-tester"
    │
    ▼
POST /chatbot/skills/install  { url: "https://github.com/acme/..." }
    │
    ▼
SkillManager.install(user_id, github_url)
    ├─ Clone repo to workspaces/{user_id}/skills/kronos-skill-stress-tester/
    ├─ Validate kronos-skill.toml exists and is valid
    ├─ pip install --target workspaces/{user_id}/site-packages/ .
    ├─ Load manifest and register tools in UserSkill model
    └─ Return skill metadata

5.3 Skill isolation

  • Each user's skills install into workspaces/{user_id}/site-packages/
  • sys.path is temporarily modified per-request to include the user's site-packages
  • Skills run in the same process but cannot access other users' workspaces
  • Skills may only call KRONOS read API and propose_workflow — they cannot directly write to the database

5.4 Security constraints

  • Only github.com URLs are permitted for install
  • Manifest is validated before any code runs
  • Tool entrypoints are imported dynamically; no exec() or shell commands
  • Skills are sandboxed by user workspace — no cross-user file access
  • Skill tools are called through the KRONOS tool router, not directly

7.2 Data models

# core/src/vaultdb/workflow/models.py

class WorkflowRun(Model):
    """Persisted workflow — DRAFT through COMPLETE."""
    __table_name__ = "workflow_run"

    workflow_id   = Text(primary_key=True, default=lambda: f"WF-{uuid4().hex[:8]}")
    name          = Text(default="")
    description   = Text(default="")
    created_by    = Text(default="")          # OIDC sub claim
    created_at    = DateTime(default=now_utc)
    block_id      = Text(default="")
    status        = Text(default="DRAFT")
    # DRAFT | PENDING_APPROVAL | APPROVED | REJECTED | RUNNING | COMPLETE | FAILED

    workflow_json = Text(default="")          # full JSON blob
    result_json   = Text(default="")          # step results after execution
    error_message = Text(default="")
    conversation_id = Text(default="")        # originating chat session


class WorkflowApproval(Model):
    """Immutable approval record — checked by WorkflowManager before execution."""
    __table_name__ = "workflow_approval"

    approval_id   = Text(primary_key=True, default=lambda: f"APR-{uuid4().hex[:8]}")
    workflow_id   = Text(default="")
    approved_by   = Text(default="")          # OIDC sub of approver
    approved_at   = DateTime(default=now_utc)
    approval_token = Text(default="")         # HMAC-signed token
    action        = Text(default="")          # APPROVED | REJECTED
    rejection_reason = Text(default="")


class WorkflowStep(Model):
    """Per-step execution record written during workflow execution."""
    __table_name__ = "workflow_step"

    step_record_id = Text(primary_key=True, default=lambda: str(uuid4()))
    workflow_id    = Text(default="")
    step_id        = Text(default="")

7.3 WorkflowManager task

# core/src/vaultdb/workflow/manager.py

@TED.task()
def submit_workflow(workflow_json: str, submitted_by: str) -> dict:
    """
    Receive workflow JSON from the chatbot, persist it, and return
    workflow_id for the UI to poll.
    Status is set to PENDING_APPROVAL.
    Does NOT execute — execution requires a separate approve() call.
    """

@TED.task()
def approve_workflow(workflow_id: str, approved_by: str, approval_token: str) -> dict:
    """
    Record approval in WorkflowApproval table and transition
    WorkflowRun to APPROVED. Triggers execute_workflow.
    """

@TED.task()
def reject_workflow(workflow_id: str, rejected_by: str, reason: str) -> dict:
    """
    Record rejection in WorkflowApproval table, transition to REJECTED.
    """

@TED.task()
def execute_workflow(workflow_id: str) -> dict:
    """
    Execute an APPROVED workflow step by step.

    Safety check:
        1. Load WorkflowRun — must be status=APPROVED
        2. Load WorkflowApproval — must exist and be APPROVED
        3. Verify HMAC approval_token matches server secret
        4. If any check fails → raise PermissionError, set status=FAILED

    Execution:
        - Topological sort of steps by depends_on
        - Execute each step in order (parallel where possible via Celery group)
        - Resolve $step_xxx.result.field references
        - Write WorkflowStep record after each step
        - On completion: set WorkflowRun.status = COMPLETE + result_json
        - On failure: set status = FAILED + error_message
    """

@TED.task()
def get_workflow_status(workflow_id: str) -> dict:
    """Poll-friendly status endpoint — returns WorkflowRun + step statuses."""

7.4 Approval token security

approval_token = HMAC-SHA256(
    key  = config.WORKFLOW_APPROVAL_SECRET,      # new env var, in Secrets Manager
    msg  = f"{workflow_id}:{approved_by}:{approved_at_iso}"
)

WorkflowManager.execute_workflow() recomputes the HMAC and rejects execution if it does not match the stored token. This prevents replay attacks and ensures the approval record was written by a legitimate server call, not a direct database edit.

12. Execution Safety — Approval Gate

                  User clicks "Approve" in UI
                            │
                            ▼
          POST /chatbot/workflow/{id}/approve
                  (requires valid Bearer token)
                            │
                            ▼
          WorkflowApproval record written to DB
          approval_token = HMAC(secret, workflow_id + user + timestamp)
                            │
                            ▼
          WorkflowRun.status → APPROVED
                            │
                            ▼
          WorkflowManager.execute_workflow.apply_async(workflow_id)
                            │
              ┌─────────────▼──────────────┐
              │  execute_workflow() runs    │
              │  in Celery worker           │
              │                            │
              │  1. Load WorkflowRun       │
              │     status must = APPROVED │──── FAIL → abort
              │                            │
              │  2. Load WorkflowApproval  │
              │     must exist + APPROVED  │──── FAIL → abort
              │                            │
              │  3. Verify HMAC token      │──── FAIL → abort
              │                            │
              │  4. Execute steps in       │
              │     topological order      │
              │                            │
              │  5. Write WorkflowStep     │
              │     result after each step │
              └────────────────────────────┘

No code path in execute_workflow bypasses all three checks. Even if an attacker directly calls the Celery task, the HMAC check (using the server-side secret) will prevent execution of an unapproved workflow.

16. Open Questions

  1. Streaming vs batch responses — Should the chat API stream tokens via SSE, or return complete responses? SSE is better UX but adds complexity to the Dash callback architecture.
  2. Conversation persistence scope — How long are conversations retained? Per session? 30 days? Tied to workflow lifetime?
  3. Skill sandboxing depth — Is process-level isolation (separate subprocess per skill) needed, or is the import-time path isolation sufficient?
  4. Multi-step approval — Some workflows may require two approvers (actuary + CIO). Should WorkflowApproval support a min_approvals: int field?
  5. Workflow versioning — If a user edits the JSON before approving, should it create a new workflow_id or version the existing one?
  6. Skill marketplace — Long term: build a curated GitHub-hosted index of vetted skills (like a KRONOS skill registry)?
  7. Audit log — All WorkflowApproval records are immutable by design. Should conversation history also be immutable (append-only) for BMA audit purposes?
