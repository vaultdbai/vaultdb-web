Architectural Evaluation: DuckLake vs. Nessie + Iceberg

Overview

This document evaluates the potential transition from the current Nessie + Apache Iceberg architecture to DuckLake for VaultDB's data layer. The primary goals of this shift are reducing operational complexity and enhancing the developer experience for sandbox workflows.

Comparison at a Glance

Feature Nessie + Iceberg (Current) DuckLake (Proposed)
Infrastructure High (Nessie Server + S3/MinIO) Low (Local DB or Postgres)
Small Writes Heavy (Multiple Parquet/Metadata files) Efficient (Inlined in Metadata DB)
Local Dev Requires Docker & Networked Services Zero-config (Local file-based)
Maturity Industry Standard / Enterprise Grade Emerging / Specialized for DuckDB
Inheritance Python-side manual merge Native SQL-level inheritance

Key Advantages of DuckLake for VaultDB

1. Unified Metadata and Data Inlining

In the current Iceberg implementation, even a 1-row update to a sandbox creates a new version of the metadata and a new Parquet data file.

DuckLake introduces Data Inlining: - Small Changes (< 10 rows): Stored directly in the SQL metadata catalog (DuckDB/Postgres). - Large Changes: Stored as Parquet files. - Impact: This drastically reduces I/O overhead for VaultDB's sandbox pattern, where users often add temporary "what-if" data for testing.

2. Operational Simplicity

Transitioning to DuckLake removes the need for: - Project Nessie Server: Eliminates a Java-based dependency and its associated JVM tuning/maintenance. - REST Catalog Bridge: Removes the complexity of mapping Iceberg REST calls to Nessie API calls. - Object Storage for Dev: Developers can run full integration tests using a single local database file instead of requiring a MinIO/S3 environment.

3. Native Data Inheritance (SQL Pushdown)

VaultDB's InheritedReader currently performs merges in Python memory using pyarrow.compute.

With DuckLake, we can leverage DuckDB's native SQL engine to perform the inheritance merge. This allows for: - Vectorized Performance: Merges happen at the engine level rather than the application level. - Predicate Pushdown: Filters can be applied during the merge, reducing the amount of data loaded into memory.

Technical Feasibility

Implementation Changes

  1. NessieCatalogManager -> DuckLakeCatalogManager: Update src/vaultdb/data/catalog.py to use the DuckLake Python API.
  2. Persistence Options:
  3. Local: DuckDB file.
  4. Shared/Dev: PostgreSQL (supported by DuckLake for metadata).
  5. Data Access: Replace pyiceberg with duckdb + ducklake extensions for reading.

Final Recommendation

DuckLake is a strong fit for VaultDB's specific requirements of lightweight sandboxing and data inheritance. The ability to inline small writes directly addresses the current system's "too many moving parts" issue while providing a more responsive developer experience for testing.
