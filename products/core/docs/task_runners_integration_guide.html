Task Runners Integration Guide

Overview

VaultDB supports multiple task runners (Celery, AWS Lambda, and AWS Batch) with a unified interface. All runners integrate with the DuckLake data layer, enabling tasks to operate within isolated "Virtual Forks" (sandboxes) using DuckDB for high-performant data access.

Quick Start

Basic Task Definition

from vaultdb import TED

# Define a task
@TED.task()
def my_task(x: int, y: int) -> int:
    """Add two numbers."""
    return x + y

# Submit task
result = my_task.apply_async(args=(5, 10), kwargs={})
print(f"Task ID: {result.task_id}")
print(f"Status: {result.status}")

Local Development vs Production

from vaultdb.core import Application

# Local Development using default sandbox logic
Application.connect()  # uses config defaults

# Production connection with OIDC authentication
Application.connect(catalogs={"default": "s3://prod-bucket/prod.ducklake"}, auth_type=AuthType.OIDC)

Switch auth context temporarily

with Application.execute_as(auth_token="user_token"): # Tasks executed here use the new catalog context result = my_task.apply_async(args=(1, 2))


## Runner-Specific Configuration

### Celery Runner (Redis)

```python
from vaultdb.celery import setup_celery

# Setup Celery runner
runner = setup_celery()

# Access underlying Celery app if needed
celery_app = runner.celery_app

Lambda Runner

from vaultdb.compute.core import get_runner, RunType

# Submit task with Lambda-specific options
result = my_task.apply_async(
    args=(1, 2),
    kwargs={},
    TED = get_runner(RunType.LAMBDA),
    function_name="my-lambda-function"
)

Batch Runner

from vaultdb.compute.core import get_runner, RunType

# Submit task with Batch-specific options
result = my_task.apply_async(
    args=(1, 2),
    kwargs={},
    TED = get_runner(RunType.BATCH),
    job_queue="my-job-queue",
    job_definition="my-job-definition",
    memory=4096,  # MB
    number_of_cpus=4,
    number_of_gpus=0
)

All tasks automatically track their status in the TaskStatus model, which is persisted to the DuckLake metadata catalog.

from vaultdb.compute.taskstatus import TaskStatus

# Get task status
task_status = TaskStatus.get_by_task_id("task-id-123")
print(f"Status: {task_status.status}")

Unified Interface

All runners implement the same interface:

# All runners have these methods:
runner.send_task(name, args, kwargs, **options)  # Submit task
runner.AsyncResult(task_id)  # Get result object
runner.tasks  # Task registry
runner.close()  # Cleanup

Testing and Mocking

Mocks in tests/conftest.py automatically patch the DuckLakeCatalogManager, ensuring that tests run against in-memory DuckDB instances without hitting production S3 buckets or infrastructure.

Configuration (Environment Variables)

# DuckLake Configuration
export CATALOG_DATA_PATH="s3://vaultdb-data"

# Celery
export SERVICE_BROKER_URL="redis://localhost:6379"

# Lambda
export COMPUTE_FUNCTION_NAME="my-lambda-function"

Best Practices

  1. Use appropriate runner for task type:
  2. Celery: Short-running, frequent tasks
  3. Lambda: Event-driven, serverless tasks

  4. Batch: Long-running, compute-intensive tasks

  5. Always track task status: Use TaskStatus to monitor task execution and audit results.

  6. Handle database context: Use execute_as() for temporary catalog/role switching.

  7. Test context correctly: Rely on the global DuckLakeCatalogManager mocks for unit testing.
