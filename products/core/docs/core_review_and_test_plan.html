VaultDB Core Review & Testing Plan

This document outlines a comprehensive plan to test, stabilize, and verify the core of VaultDB. This will ensure confidence in its functionality before migrating to building reinsurance models, as well as prepare it for a standalone public release.

Current State Assessment

Based on the review of the codebase, documentation (ducklake.md, system-context.md, TASK_RUNNER_ARCHITECTURE.md), and the recent local test runs, here is the current state: - Automated Tests: A recent pytest execution showed 880 passed, 27 failed. The failures are primarily in the DuckLake data layer (IO Error: No files found that match the pattern "None/*.parquet") due to a missing or unmocked CATALOG_DATA_PATH, and in the GeminiBackend crawler advisor. - Task Runners: Unified interface implemented across Celery, AWS Batch, and Lambda. - DuckLake: Powerful "Virtual Fork" engine, but needs verification for S3 paths and concurrent-writer semantics. - Workflows: Fully featured with triple-gate approval, but lacks an immutable artifact store and TOCTOU protection (per TODO.md).

Strategic Plan

We will tackle the core review and testing in 6 phases. You can prompt me to execute any of these phases one by one.

Phase 1: Test Suite Stabilization (Fixing the 27 Failures)

Before deep E2E testing, the foundational unit tests must be green. - Tasks you can ask me to do: - "Fix the DuckLake IO Error failing tests in tests/data/test_data.py and tests/data/test_transactions.py." - "Fix the GeminiBackend tests in tests/test_crawler/test_advisor.py." - "Run a full pytest suite and ensure we achieve 100% pass rate."

Phase 2: DuckLake Storage & Concurrency E2E (Crucial for Reinsurance)

Reinsurance models require heavy data manipulation. DuckLake needs to be rock solid. - Tasks you can ask me to do: - "Write an E2E test script to verify DuckLake behavior locally." - "Write a test to verify DuckLake interactions with S3 (mocked via moto or a local MinIO container)." - "Implement the DuckLake concurrent-writer protection (as mentioned in TODO.md deferred item #8) using Redis locks." - "Audit the TimeSeriesModel and Model pushdown logic for performance bottlenecks."

Phase 3: Task Orchestration & Workflow Robustness

The unified task runner (TED) and Workflow engine must orchestrate reinsurance pipelines reliably. - Tasks you can ask me to do: - "Review the runner.py and task execution proxies to ensure correct behavior across Local and Service runners." - "Write E2E tests for the Workflow approval engine." - "Implement the TOCTOU (Time-of-Check to Time-of-Use) protection on Workflow verify -> execute (TODO #7)." - "Add the immutable artifact store (append-only archive bucket) for ApprovalRecord compliance (TODO #6)."

Phase 4: Crawler & LLM Advisers

Ensuring the multi-provider LLM abstraction works flawlessly for any data extraction needs. - Tasks you can ask me to do: - "Review the crawler/ module and ensure lazy-initialization is working for all LLM backends." - "Create test stubs for Ollama, OpenAI, Anthropic, Bedrock, and Gemini backends."

Phase 5: Web API & Auth Verification

Testing the external-facing capabilities. - Tasks you can ask me to do: - "Run a local instance of the FastAPI dashboard and test task submission and revocation." - "Review the OIDC and basic authentication flows in vaultdb.auth."

Phase 6: Standalone Release Preparation

Preparing the codebase for the world to use. - Tasks you can ask me to do: - "Review setup.py, pyproject.toml, and MANIFEST.in for public packaging." - "Check the core codebase for any hardcoded proprietary references that shouldn't be in the open-source/standalone version." - "Generate infrastructure-as-code (Terraform or CloudFormation) to deploy the required Redis and S3 components."

How to Proceed

I recommend starting with Phase 1 to fix the broken tests. Would you like me to begin fixing the DuckLake testing path issues and the GeminiBackend crawler failures?
