Workflow System — Architecture & Design

The VaultDB workflow system enables AI-proposed multi-step computational pipelines that require human approval before execution. This document covers the full lifecycle from proposal to execution.

Overview

When the KRONOS AI chatbot proposes a workflow (e.g., "Q1 2026 Valuation Pipeline"), it defines a directed acyclic graph (DAG) of steps. Each step maps to a TED task in a domain submodule. The workflow must be reviewed and approved by a human before any step executes.

Lifecycle State Machine

stateDiagram-v2
    [*] --> PENDING_APPROVAL: AI proposes workflow
    PENDING_APPROVAL --> APPROVED: Human approves (HMAC token created)
    PENDING_APPROVAL --> REJECTED: Human rejects
    APPROVED --> RUNNING: execute_workflow() called
    RUNNING --> DONE: All steps complete
    RUNNING --> FAILED: Step fails (on_failure=abort)
    REJECTED --> [*]
    DONE --> [*]
    FAILED --> [*]

Data Models

WorkflowRun

The top-level record representing one proposed workflow. Stored in the workflow_run DuckLake table.

Field Type Description
workflow_id Text (PK) UUID, auto-generated
user_id Text OIDC subject of the proposing user
block_id Text KRONOS block identifier (e.g., TED-FA-2026)
name Text Human-readable name
description Text Optional free-text
status Text Lifecycle state (see diagram above)
definition JSON Full workflow definition including steps array
step_count Integer Total number of steps
steps_done Integer Steps completed successfully
created_at DateTime When the AI proposed the workflow
started_at DateTime When execution began
finished_at DateTime When execution completed or failed

WorkflowStep

One step within a workflow run. Composite primary key: (workflow_id, step_id).

Field Type Description
step_id Text (PK) Unique within the run (e.g., step_001)
step_index Integer 0-based execution order after DAG resolution
name Text Human-readable step name
task Text Dotted task path (e.g., liability.tasks.project_cash_flows)
kwargs JSON Task arguments; supports $step_xxx.result.field references
depends_on JSON List of step IDs that must complete first
timeout Integer Max seconds (default 600)
on_failure Text "abort" (stop run) or "continue" (skip dependents)
status Text PENDING, RUNNING, DONE, FAILED, SKIPPED
result JSON Task return value
celery_task_id Text Celery task UUID for async tracking

Workflow Definition JSON

The AI chatbot proposes a workflow as a JSON definition:

{
  "name": "Q1 2026 Valuation Pipeline",
  "description": "Full valuation of TED-FA-2026 block",
  "steps": [
    {
      "id": "step_001",
      "name": "Project Cash Flows",
      "task": "liability.tasks.project_cash_flows",
      "kwargs": {"block_id": "TED-FA-2026", "n_periods": 360},
      "depends_on": [],
      "timeout": 600,
      "on_failure": "abort"
    },
    {
      "id": "step_002",
      "name": "Price Asset Portfolio",
      "task": "asset.tasks.price_portfolio",
      "kwargs": {"portfolio_id": "$step_001.result.portfolio_id"},
      "depends_on": ["step_001"],
      "timeout": 300,
      "on_failure": "abort"
    }
  ]
}

Step Reference Syntax

Steps can reference results from previous steps using the $step_xxx.result.field syntax. The workflow manager resolves these at execution time:

"$step_001.result.run_id"  →  resolves to the value of step_001's result["run_id"]

TED Task Functions

submit_workflow

Persists a new WorkflowRun and its WorkflowStep rows. Called by ChatHub when the AI proposes a workflow. Status starts as PENDING_APPROVAL.

get_workflow

Fetches a WorkflowRun with all its steps, sorted by step_index.

list_workflows

Lists WorkflowRun records for a user, newest first (default limit: 20).

execute_workflow

The critical function. Performs the triple-gate approval check before running any step:

flowchart TD
    START["execute_workflow(workflow_id)"] --> GATE1
    GATE1{"Gate 1: ApprovalRecord exists?"} -->|No| FAIL1["WorkflowApprovalError"]
    GATE1 -->|Yes| GATE2
    GATE2{"Gate 2: is_valid == True?"} -->|No| FAIL2["WorkflowApprovalError"]
    GATE2 -->|Yes| GATE3
    GATE3{"Gate 3: HMAC token verifies?"} -->|No| FAIL3["WorkflowApprovalError"]
    GATE3 -->|Yes| TOPO["Topological sort steps"]
    TOPO --> EXEC["Execute steps in DAG order"]
    EXEC --> RESOLVE["Resolve $step_xxx refs"]
    RESOLVE --> CALL["_call_task(dotted_name, kwargs)"]
    CALL --> NEXT{"More steps?"}
    NEXT -->|Yes| EXEC
    NEXT -->|No| DONE["WorkflowRun.status = DONE"]

Execution Model

  1. Steps are run in-process in topological order (Kahn's algorithm).
  2. Step results are accumulated in a step_results dict.
  3. $step_xxx.result.field placeholders are resolved from step_results.
  4. If a step fails and on_failure == "abort", the run is marked FAILED immediately.
  5. If on_failure == "continue", the failed step's dependents are SKIPPED.

update_step_status

Updates a single step's status, result, or error message. Used by async execution to report progress.

Security Guarantee

execute_workflow never runs without cryptographic proof of human approval:

  • The ApprovalRecord is created by ChatHub after the actuary clicks "Approve" in the dashboard.
  • The HMAC token binds the approval to: approval_id, subject_id, subject_type, approver_id, approver_email, approved_at.
  • UserProcesses never receive the WORKFLOW_APPROVAL_SECRET, so they cannot forge tokens.
  • The triple-gate is checked at execution time, not at approval time — a revoked approval blocks execution even if it was previously approved.

Integration Points

Component Role
ChatHub (dashboard/chatbot/hub.py) Receives workflow proposals, calls submit_workflow, creates ApprovalRecord
Dashboard UI (dashboard/pages/chatbot.py) Renders workflow DAG, approval buttons, step details
Workflow Viewer (dashboard/pages/workflow_viewer.py) Dedicated page for workflow inspection and approval
Approval Panel (dashboard/components/approval_panel.py) Reusable UI component for approval actions
Policy Enforcer (core/src/vaultdb/approval/policy.py) Validates approval against configurable rules
