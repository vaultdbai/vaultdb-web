Infra Deploy Runbook — Cognito + scoped roles

A step-by-step you can follow without re-reading the plan docs. Three phases: one-time admin bootstrap, dev workflow (Google login), per-session loop (deploy → test → tear down).

Background / why each step exists: - infrastructure/docs/INFRASTRUCTURE_REVIEW_PLAN.md §1.4.5 + §1.4.6 - core/docs/E2E_TESTING_STRATEGY.md - /vaultdb/CLAUDE.md → "AWS Connectivity & Credentials"

Always tear down dev/staging stacks before walking away. The stack has hourly-billed resources that keep charging even when ECS is at 0.

How auth works (read this once)

   ┌───────────────────┐       OIDC          ┌─────────────────────┐
   │  dev's browser    │  ────────────────▶  │  Cognito Identity   │
   │ (vaultdb-auth)    │   (Google,          │  Pool (in bootstrap │
   └───────────────────┘   Microsoft Entra,  │  stack)             │
                           Okta, Auth0, …)   └──────────┬──────────┘
                                                        │ role mapping by email
                                          ┌─────────────┴────────────┐
                                          ▼                          ▼
                              admin email  →  DEPLOYER role     else → DATA role
                                          │                          │
                                          ▼                          ▼
                                   CloudFormation +              S3 / DuckLake /
                                   PassRole                      invoke runners

The bootstrap supports ANY combination of Google (social shortcut) and one generic OIDC provider (Microsoft Entra ID, Okta, Auth0, Keycloak — anything IAM can register as an OIDC provider). Same admin- email allow-list applies across whichever IdPs you configure.

No IAM users. No static keys. Off-boarding = remove the email from the bootstrap template and re-bootstrap.

Phase 1 — ADMIN does this ONCE per environment

Requires admin AWS credentials (the only time admin is ever used). Also requires a Google OAuth Client ID — see Phase 1.0.

1.0 — (One-time) configure your IdP

Pick ONE or BOTH paths:

Path A — Google (easiest, no IAM setup):

In Google Cloud Console → APIs & Services → Credentials:

  1. Create OAuth Client → Web application.
  2. Authorised redirect URI: https://<your-app-host>/oauth/callback (or http://localhost:<port>/oauth/callback for local dev).
  3. Save the Client ID (looks like 1234567890-abc.apps.googleusercontent.com).

Path B — Any OIDC provider (Microsoft Entra ID, Okta, Auth0, Keycloak, …):

Admin pre-registers the IdP in IAM as an OIDC provider (one-time, ~30s):

# Microsoft Entra ID v2.0:
aws iam create-open-id-connect-provider \
    --url https://login.microsoftonline.com/<tenant>/v2.0 \
    --client-id-list <your-app-client-id> \
    --thumbprint-list <cert-thumbprint>

# Okta:
aws iam create-open-id-connect-provider \
    --url https://<your-org>.okta.com \
    --client-id-list <your-app-client-id> \
    --thumbprint-list <cert-thumbprint>

Capture (a) the resulting OIDC provider ARN, and (b) the issuer URL without the https:// prefix (e.g. login.microsoftonline.com/<tenant>/v2.0 or acme.okta.com).

1.1 — Bootstrap Cognito + scoped roles

ACCT=$(aws sts get-caller-identity --query Account --output text)

# Google only:
bash core/scripts/bootstrap_deploy_role.sh vaultdb dev us-east-1 \
    --admin-email alice@example.com \
    --google-client-id 1234567890-abc.apps.googleusercontent.com

# Microsoft Entra only:
bash core/scripts/bootstrap_deploy_role.sh vaultdb dev us-east-1 \
    --admin-email alice@example.com \
    --oidc-provider-arn arn:aws:iam::$ACCT:oidc-provider/login.microsoftonline.com/tenantid/v2.0 \
    --oidc-issuer-host login.microsoftonline.com/tenantid/v2.0

# Okta + a second admin:
bash core/scripts/bootstrap_deploy_role.sh vaultdb dev us-east-1 \
    --admin-email alice@example.com --admin-email-2 bob@example.com \
    --oidc-provider-arn arn:aws:iam::$ACCT:oidc-provider/acme.okta.com \
    --oidc-issuer-host acme.okta.com

# Google + Okta (federate both):
bash core/scripts/bootstrap_deploy_role.sh vaultdb dev us-east-1 \
    --admin-email alice@example.com \
    --google-client-id 123-abc.apps.googleusercontent.com \
    --oidc-provider-arn arn:aws:iam::$ACCT:oidc-provider/acme.okta.com \
    --oidc-issuer-host acme.okta.com

# Outputs (save these — devs need them):
#   IdentityPoolId       us-east-1:abcd-...
#   DataRoleArn          arn:aws:iam::ACCT:role/vaultdb-dev-data-role
#   DeployerRoleArn      arn:aws:iam::ACCT:role/vaultdb-dev-deployer-role
#   CfnExecutionRoleArn  arn:aws:iam::ACCT:role/vaultdb-dev-cfn-exec-role

That's it for admin — until you need to add/remove an admin email (re-run with the updated list — CloudFormation updates in place) or delete the env entirely (teardown_infra.sh --teardown-bootstrap, admin-only).

Phase 2 — DEV setup (one-time per laptop)

# 2.1 — Configure VaultDB to use the Identity Pool from Phase 1.1
# (put this in your .env or shell profile)
export USER_IDENTITY_POOL_ID=us-east-1:abcd-...
export aws_region=us-east-1
export aws_profile=dev

# 2.2 — Verify vaultdb-auth flow works (will open a browser for Google login)
vaultdb-auth

# 2.3 — Confirm which role you got
export AWS_PROFILE=dev
aws sts get-caller-identity
# If your email is on the admin list: assumed-role/vaultdb-dev-deployer-role/...
# Otherwise:                          assumed-role/vaultdb-dev-data-role/...

If 2.3 shows the data-role when you expected deployer, your email isn't on the admin list — ask the admin to add it to AdminEmail2/3 and re-run bootstrap (idempotent).

Phase 3 — Per-session loop (DEPLOY → TEST → TEAR DOWN)

3.1 Sign in (every session)

vaultdb-auth creds expire after ~1 hour. Re-run any time you get expired-credential errors.

vaultdb-auth                                  # interactive IdP login (Google / Microsoft / Okta / …)
export AWS_PROFILE=dev
aws sts get-caller-identity                   # should be deployer role

3.2 Fill in the params file (first time only)

cp infrastructure/cloudformation/params-dev.json.example \
   infrastructure/cloudformation/params-dev.json     # gitignored — has secrets

# Edit params-dev.json — fill in placeholders flagged by the script:
#   VpcId / Public+Private Subnet IDs   (BYO existing VPC + 2 public + 2 private)
#   SupervisorPassword                  (your choice)
#   ApprovalSecretKey                   → openssl rand -hex 32
#   AdminEmail, DemoUserEmail
#   AuthClientId/AuthClientSecret       (the SAME Google client ID + secret)

3.3 DEPLOY

bash core/scripts/deploy_infra.sh vaultdb dev us-east-1
# - Auto-discovers DEPLOY_ROLE_ARN from the bootstrap stack
# - Validates params-dev.json (fails fast on placeholders)
# - Uploads templates to s3://vaultdb-dev-templates-us-east-1
# - cloudformation deploy --role-arn $DEPLOY_ROLE_ARN
# Wait ~10–20 min for nested stacks to converge.

After it returns CREATE/UPDATE_COMPLETE:

aws cloudformation describe-stacks \
    --stack-name vaultdb-dev-stack \
    --query 'Stacks[0].Outputs' --output table
# Note: S3BucketName, LoadBalancerDNS, LambdaFunctionName,
#       CPUSpotJobQueueArn, CPUJobDefinitionArn, ApprovalSecretArn,
#       IdentityPoolId (same as bootstrap output — sourced via ImportValue)

3.4 TEST

You're still signed in as DEPLOYER. For S3 / DuckLake / data-plane tests, you have a choice:

  • Stay on deployer creds — has data-plane perms inherited from cfn-exec
  • templates bucket. Fine for quick smoke tests.
  • Switch to a separate data-role session — more realistic; mirrors what an end user gets: bash # Easiest: switch to a non-admin Google account that Cognito maps to DataRole vaultdb-auth # log in as a non-admin user

Then run whatever E2E phase you're at — see E2E_TESTING_STRATEGY.md: - P3 — Real Redis (broker URL from RedisStack outputs) - P4 — S3 DuckLake (CATALOG_DATA_PATH=s3://vaultdb-dev-data) - P5 — Batch + Lambda (submit a test job to CPUSpotJobQueueArn / Lambda)

3.5 TEAR DOWN (mandatory — do this before walking away)

[!NOTE] Automated 1-Hour Self-Destruct (Dev Only): In Environment=dev, the stack deploys a serverless self-destruct mechanism (EventBridge Rule + Lambda). Exactly 1 hour after deployment, this will automatically empty all ephemeral data buckets and trigger a CloudFormation stack deletion. This is a fallback to save money if you forget to run the manual teardown script. To test or terminate early, always run the manual teardown script below.

bash core/scripts/teardown_infra.sh vaultdb dev us-east-1
# - Empties versioned S3 buckets explicitly (does NOT trust S3CleanupLambda)
# - cloudformation delete-stack + waits for completion
# - Refuses to run on prod
# Confirmation prompt: type "dev" to proceed.

Optional flags:

  • --delete-templates-bucket — also delete vaultdb-dev-templates-us-east-1 (the script-managed bucket, not part of the stack).
  • --teardown-bootstrap — also delete the bootstrap stack (Identity Pool + deployer + cfn-exec roles). Needs admin creds. Only do this if you're fully done with the environment; otherwise next deploy needs a re-bootstrap (Phase 1).
  • --yes — skip the confirmation prompt (for CI / scripted runs).

3.6 Verify the bill is going to zero

aws cloudformation list-stacks --region us-east-1 \
    --stack-status-filter CREATE_COMPLETE UPDATE_COMPLETE
# Should NOT list vaultdb-dev-stack.

# Spot-check the hourly-billed resources are gone:
aws elasticache describe-cache-clusters \
    --query 'CacheClusters[?starts_with(CacheClusterId,`vaultdb-dev`)].CacheClusterId'
aws elbv2 describe-load-balancers \
    --query 'LoadBalancers[?starts_with(LoadBalancerName,`vaultdb-dev`)].LoadBalancerName'
# Both should return empty arrays.

The bootstrap stack itself is free to leave up (it's just IAM + Cognito — no hourly charges). Tear it down only when retiring the environment.

What costs money (and how fast)

These keep billing even when ECS Fargate is scaled to 0 — the reason teardown matters:

Resource Idle bill? ~Rate (us-east-1) Dev note
ElastiCache Redis YES ~$0.016/hr/node (cache.t4g.micro) biggest sleeper
Application LB YES ~$0.022/hr + per-LCU
EFS yes (small) ~$0.30/GB-month
NAT Gateway YES ~$0.045/hr + $0.045/GB processed $0 for dev (see below)
VPC endpoints YES (opt-in) ~$0.10/hr (5 × 2 AZ × $0.01)
ECS Fargate tasks only if Min>0 default MinCapacity=0 → free
Batch / Lambda only on run Spot-priced; idle = 0
S3 / ECR storage pennies persistent — fine to leave
Bootstrap stack $0 IAM + Cognito = free at idle
Persistent bucket pennies ~$0.023/GB-month (reference data) survives teardown

Leaving the master-stack up for a 24-hour weekend ≈ $1–$3 of nothing (more with DeployVpcEndpoints=true, see below).

Dev gets $0 networking automatically

When Environment=dev, ECS Fargate tasks run in public subnets with AssignPublicIp=ENABLED. Outbound internet goes directly through the Internet Gateway (free) — no NAT Gateway needed. Savings: ~$32/month per dev environment.

This is automatic — no parameter to set. Staging and prod always use private subnets with AssignPublicIp=DISABLED (requires NAT for outbound). Security groups still gate inbound in all environments; the public IP is for outbound only (ECR pulls, Secrets Manager, external APIs).

Batch stays in private subnets regardless of environment. AWS Batch EC2/SPOT compute doesn't support AssignPublicIp. Batch jobs still need NAT or VPC endpoints for outbound. This is fine because Batch is idle-cost-free (MinvCpus=0) — NAT only costs money when jobs actually run.

The NAT Gateway question (staging/prod)

NAT lives in your BYO-VPC, not in this stack. Compute in private subnets needs some outbound path to: - pull ECR images, hit Secrets Manager / CloudWatch Logs / STS, - reach external APIs (Anthropic, Gemini, OIDC IdP, prospectus crawler targets, OS package mirrors).

You have three topologies for staging/prod:

  1. NAT only — simplest, works for everything. ~$32/month idle + per-GB. Recommended for prod.

  2. VPC endpoints, no NAT — set DeployVpcEndpoints=true in your params file. Creates 5 interface endpoints (ECR API / DKR / Secrets / Logs / STS) + free S3 gateway. ~$72/month idle for the endpoints. AWS-only traffic works; external HTTPS breaks. Anything that calls Anthropic / OIDC IdP / external sites must move to a public subnet (set assignPublicIp=ENABLED on those task definitions) or you keep a small dedicated NAT just for them.

  3. No NAT, public subnets, no endpoints — cheapest ($0 networking). Compute gets public IPs; security groups still gate ingress. Fine for dev (this is the default for Environment=dev); security people will hate it for staging/prod.

Recommendation for VaultDB staging: option 1 (NAT). The endpoint cost ($72/mo) actually exceeds the NAT idle cost ($32/mo) at typical dev volumes — endpoints only win when you're processing serious data through them. Revisit at scale if NAT data charges ever climb.

If you want option 2, set DeployVpcEndpoints=true AND fill in PrivateRouteTable1Id/PrivateRouteTable2Id in params-dev.json (skip those and you lose the free S3 gateway endpoint, which makes ECR image pulls 10× more expensive — they go via the interface endpoint instead of the gateway).

Persistent reference data

The master-stack's data bucket (${project}-${env}-data) is deleted on teardown — that's by design (stop the bill). But re-uploading census files, DuckLake baselines, and reference datasets every session is painful.

Solution: a persistent bucket (${project}-${env}-persistent) deployed as a standalone stack. DeletionPolicy: Retain ensures it survives even if the stack itself is deleted. Cost: pennies/month.

# Deploy once per environment (standalone — not part of master stack):
aws cloudformation deploy \
    --template-file infrastructure/cloudformation/persistent-data-bucket.yaml \
    --stack-name vaultdb-dev-persistent-data \
    --parameter-overrides ProjectName=vaultdb Environment=dev

# Seed it with reference data:
aws s3 cp kronos_synthetic_census.csv s3://vaultdb-dev-persistent/census/
aws s3 cp my-ducklake-baseline/ s3://vaultdb-dev-persistent/ducklake/ --recursive

# In your app config, point secondary paths here:
export PERSISTENT_DATA_PATH=s3://vaultdb-dev-persistent

teardown_infra.sh explicitly does not touch this bucket — it only empties the ephemeral ${project}-${env}-data bucket.

Common gotchas

  • vaultdb-auth gives me DataRole instead of DeployerRole. Your IdP email isn't in the bootstrap's admin list. Either:
  • Sign in with the admin account, OR

  • Have the admin re-run bootstrap_deploy_role.sh with your email added (idempotent — same command, just --admin-email-2 you@…).

  • vaultdb-auth errors with "no Identity Pool". USER_IDENTITY_POOL_ID env var isn't set or points at a stale pool. Check the bootstrap stack outputs: bash aws cloudformation describe-stacks --stack-name vaultdb-dev-bootstrap \ --query "Stacks[0].Outputs[?OutputKey=='IdentityPoolId'].OutputValue"

  • OIDC login lands on DataRole even though I'm an admin. Two likely causes:

  • Wrong issuer host. Cognito uses the issuer URL (minus https://) as the role-mapping key. If --oidc-issuer-host doesn't match the iss claim in your IdP's ID token exactly, the rule never fires. Check by decoding your ID token at jwt.io.

  • Email claim missing. Some IdPs (Entra "personal Microsoft account" apps) emit preferred_username instead of email. Edit the Claim field in bootstrap-deploy-role.yaml's RoleMappings.oidc block.

  • Deploy fails with User … not authorized to perform: <action> — the cfn-exec-role is missing that action. It's intentionally scoped; add the action (project-scoped) to infrastructure/cloudformation/bootstrap-deploy-role.yaml, re-run the admin bootstrap (1.1) to update, then retry the deploy. Expect a few of these on the very first deploy in a fresh account.

  • Session expires mid-deploy — vaultdb-auth issues 1-hour creds. If a CFN deploy takes longer (rare; usually 10–20 min), vaultdb-auth again and rerun deploy_infra.sh. CloudFormation resumes from where it left off.

  • Teardown hangs on stack delete — usually a non-empty S3 bucket. The script's explicit empty step covers vaultdb-dev-data, but ECR repositories with images, or the templates bucket if writes happened outside the script, will block. CloudFormation will show the failing resource — clear it and rerun teardown.

  • vaultdb-auth always wants to open a browser. Headless / WSL / SSH-only? You can drive the OIDC flow with a device code grant — see core/docs/auth.md (not yet written; same vaultdb-auth binary takes --device once that lands).

  • CI can't log into an IdP interactively. Use the escape hatch: bootstrap with --extra-deployer-arn <ci-role> (GitHub OIDC role, SSO permission-set role, etc.), and CI uses assume_deployer.sh instead of vaultdb-auth. Cognito stays the primary path; CI is the exception.
