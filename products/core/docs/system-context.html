SYSTEM RULES [DO NOT OVERRIDE]

This file contains the absolute source of truth for this project. Before suggesting any code, verify it aligns with the standards below.

System Context: VaultDB

VaultDB Core Mission VaultDB is an advanced data orchestration and execution layer designed for high-performance financial and enterprise workloads. It provides isolated, branchable data sandboxes ("Virtual Forks") using a DuckLake and DuckDB architecture. It enables analysts to manipulate production-inherited data safely in isolated sandboxes, perform vectorized computations (Arrow/DuckDB), and then propagate or discard changes without impacting the upstream production environment.

* Language: Python 3.12+ (Strict typing: disallow_untyped_defs = True) * Data Lakehouse: DuckLake (DuckDB-backed, Parquet on S3) * In-Memory Engine: Apache Arrow (pyarrow), DuckDB (integrated via DuckLake, version >= 1.5.0) * Task Runners: Celery (Redis), AWS Batch, AWS Lambda * Web API: FastAPI * Caching: Redis * LLM Backends: Ollama (Gemma default), OpenAI, Anthropic (Claude), AWS Bedrock, Google Gemini, HuggingFace Transformers * Tooling: Ruff (Formatter/Linter, 160 char limit), MyPy, Pytest

Project Map

  • /src/vaultdb/: Base package.
    • core.py: Application class for connection management (DuckLake attach, S3 secrets).
    • data/: Data layer (DuckLake/Inheritance).
      • catalog.py: DuckLakeCatalogManager — manages DuckDB/DuckLake connection, sandbox schemas, and data I/O.
      • reader.py: InheritedReader — merge-and-override reads across main→sandbox hierarchy via SQL pushdown.
      • timemachine.py: Point-in-time historical queries on DuckLake versions/timestamps.
      • model.py: ORM-like Model base class mapping Python objects to DuckLake tables; inherits from main snapshots.
      • columns.py / usertype.py: Column descriptors and user-defined types with Arrow schema mapping.
    • compute/: Universal execution framework (Runner interfaces). TED proxy singleton in _state.py routes @TED.task() to the active runner.
    • batch/ | function/: AWS Batch and Lambda runners.
    • service/: Celery task runner service.
    • scheduler/: Business calendars and task scheduling.
    • cache/: Redis-based caching.
    • auth/: Authentication — AuthType.BASIC, AuthType.OIDC, AuthType.GITHUB. OIDC yields AWS credentials for S3 access.
    • web/: FastAPI app.
    • crawler/: Intelligent web crawling with multi-provider LLM support.
      • advisor.py: BaseLLMAdvisor — multi-backend LLM abstraction (Ollama, OpenAI, Claude, Bedrock, Gemini, transformers).
      • config.py: CrawlerConfig — configuration dataclass with env var overrides for all LLM providers.
      • http.py: HttpClient — session management, rate limiting, UA rotation.
      • browser.py: Playwright browser helpers (launch, overlays, dropdowns, iframes, accordions).
      • links.py: LinkClassifier — link classification with scoring and optional LLM integration.
      • search.py: WebSearcher — Google and DuckDuckGo HTML scraping.
      • content.py: Content validation, text extraction, junk detection, PDF/HTML handling.
      • files.py: FileManager — document saving, deduplication, content hashing.
    • workflow/: Workflow orchestration with triple-gate approval.
    • approval/: Approval engine and policy enforcement.
    • skills_installer/: GitHub skill installer.
    • config.py: SOLE AUTHORITY for configuration.
    • logger/: Centralized structured logging.
  • /tests/: Unit and integration tests (using pytest + unittest).
  • /docs/: Detailed project documentation.

Crawler LLM Architecture

The crawler/ package provides a pluggable multi-provider LLM layer via BaseLLMAdvisor. All backends are lazily initialised — no API call is made until generate() or available is first invoked.

Supported Backends

Backend Config env vars Default model Vision
ollama OLLAMA_URL, OLLAMA_MODEL gemma3:4b Yes
openai OPENAI_API_KEY, OPENAI_MODEL gpt-4o-mini Yes
anthropic ANTHROPIC_API_KEY, ANTHROPIC_MODEL claude-sonnet-4-6 Yes
bedrock BEDROCK_REGION, BEDROCK_MODEL anthropic.claude-sonnet-4-6-v1:0 Yes
gemini GEMINI_API_KEY, GEMINI_MODEL gemini-2.0-flash Yes
transformers LLM_MODEL Qwen/Qwen2.5-1.5B-Instruct No
none — — No

Select a backend via LLM_BACKEND env var (default: ollama).

pip install "vaultdb.core[crawler-openai]"       # OpenAI only
pip install "vaultdb.core[crawler-anthropic]"     # Claude only
pip install "vaultdb.core[crawler-bedrock]"       # Bedrock only
pip install "vaultdb.core[crawler-gemini]"        # Gemini only

For Antigravity

  • Analyze the repository structure based on the Project Map. Use this context to maintain architectural alignment during complex refactors.
  • Use Graphify graphs as your primary navigation aid. Before performing any multi-file refactor or cross-module analysis, generate a knowledge graph using /graphify on the target directories. The graph communities map directly to architectural boundaries:
    • data/ community → DuckLake/Arrow data layer
    • compute/ community → TED task dispatch
    • crawler/ community → web crawling + LLM advisor layer
    • workflow/ + approval/ community → orchestration + triple-gate security
    • web/ + service/ community → FastAPI + Celery surface area
  • When the graph shows edges crossing community boundaries, treat those as high-risk change points that require extra test coverage.
  • Prefer the graph's cluster view over manual grep/find for discovering which files to modify during a refactor.

For All AI Tools

  • Graphify-first workflow: Any time you are asked to "understand", "map", "audit", or "refactor" a section of this codebase, your first step should be to produce a knowledge graph of the relevant source tree. This gives you a machine-readable dependency map that is more reliable than heuristic file scanning.
  • The knowledge graph JSON output (nodes + edges + communities) can be fed back into subsequent prompts for targeted analysis of specific clusters.

Behavioral Guardrails (No-Go Zones)

  • Strict Configuration: NEVER use os.getenv or os.environ directly in business logic. All parameters must be mapped in src/vaultdb/config.py and accessed via vaultdb.config. (Exception: crawler/config.py uses os.environ.get in dataclass defaults for crawler-specific LLM settings — this is intentional and scoped.)
  • No Prints: NEVER use print(). Use the internal logger: logger = get_logger(config.LOGGER_*).
  • Vectorization First: Prefer pyarrow compute kernels or DuckDB SQL over iterative Python loops for any data manipulation.
  • Interface Consistency: New runners must implement the Runner interface to remain compatible with the TED (Task Execution Dispatcher) singleton.
  • Sandbox Isolation: ALWAYS use user-specific schemas (sandbox_<role>) for any non-production writes.
  • Pristine Workspace: Always clean up temporary execution scripts or scratch files (/tmp/*.py) immediately after verification.
  • LLM Backend Isolation: Never hard-code a specific LLM provider in business logic. Always go through BaseLLMAdvisor.generate() — the backend is selected by config, not by the caller.

Workflow Commands

  • /refactor: Check for os.getenv violations, missing type hints (functions, variables, class attributes, module-level vars), and ensure pyarrow/DuckDB is used for data processing. Run mypy src/ and fix all reported errors before considering the refactor complete.
  • /test: Execute python -m pytest -v on relevant modules.
  • /ducklake: Verify DuckLake catalog connectivity, inlining row limits, and inherited read SQL pushdown.
  • /graphify: Generate a knowledge graph of the target source tree for architectural understanding and dependency analysis.

Coding Standards & Quality

Ruff & General Style

  • Primary Tool: ruff is the exclusive tool for linting and formatting.
  • Line Length: Strict 160 character limit.
  • Quotes: Use double quotes (") for all string literals.
  • Imports: Single-line imports only (forced via ruff).
  • Typing: Mandatory type hints everywhere — see detailed rules below.
  • Logging: Use get_logger(config.LOGGER_*). Use f-strings for clarity.

Typing Standards (Strict — No Exceptions)

MyPy is configured with disallow_untyped_defs = True. ALL code must pass mypy src/ without errors.

Always add from __future__ import annotations at the top of every file to enable PEP 563 postponed evaluation.

Functions and methods * Every parameter must have an explicit type annotation, including self (no annotation) and cls (no annotation). * Every function and method must declare a return type, including -> None for procedures. * *args and **kwargs must be typed (e.g., *args: int, **kwargs: str).

# CORRECT
def process(self, table: str, limit: int = 100) -> list[dict[str, Any]]: ...
async def fetch(self, key: str) -> bytes | None: ...

# WRONG — missing return type and parameter type
def process(self, table, limit=100): ...

Variables * Annotate all module-level variables and class-level attributes explicitly. * Annotate local variables when the type is not immediately obvious from the right-hand side (e.g., empty collections, None assignments, results of untyped third-party calls).

# CORRECT
TIMEOUT: int = 30
_cache: dict[str, bytes] = {}
result: list[str] = []

# WRONG — unannotated module var and ambiguous local
TIMEOUT = 30
result = []

Class attributes * Declare all instance attributes in __init__ or via ClassVar / dataclass fields with full annotations. * Use ClassVar[T] for class-level constants shared across instances.

class Reader:
    _registry: ClassVar[dict[str, type[Reader]]] = {}

    def __init__(self, schema: str) -> None:
        self.schema: str = schema
        self._conn: duckdb.DuckDBPyConnection | None = None

Collections and generics * Always parameterize generic types: list[str], dict[str, Any], tuple[int, ...], set[str]. * Prefer built-in generics (list, dict, tuple, set) over typing.List / typing.Dict (Python 3.9+). * Use X | Y union syntax instead of Optional[X] or Union[X, Y] (Python 3.10+, enabled by from __future__ import annotations).

Type aliases and Protocols * Define type aliases at module level for complex repeated types: SchemaName = str, RowDict = dict[str, Any]. * Use typing.Protocol for structural interfaces rather than Any.

Implementation rule Whenever you write or modify code, immediately add missing annotations. Never leave a function, method, module variable, or class attribute without a type annotation. When reviewing or refactoring existing code, treat every missing annotation as a bug to fix.

Testing Standards (TDD Mandatory)

  • Framework: pytest + unittest.mock.
  • Coverage Goal: Aim for >90% coverage on all new features.
  • Mirroring: Tests must mirror the source tree: src/vaultdb/data/foo.py -> tests/vaultdb/data/test_foo.py.
  • Scenario Requirements:
    • Happy Path: Standard successful execution.
    • Edge Cases: Boundary values (nulls, empty lists).
    • Error Handling: Verify specific exceptions are raised.
    • Isolation: ALWAYS mock Redis, AWS, and Cloud catalogs. Use local DuckDB (:memory:)/DuckLake for data layer tests.
