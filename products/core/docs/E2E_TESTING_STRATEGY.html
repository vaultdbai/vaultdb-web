VaultDB Core — End-to-End Testing Process

Purpose. Validate every core subsystem and all four compute service types so other modules (asset, market, liability, …) can depend on core with confidence. This is a process, not a wish list: phased, gated, with owners, entry criteria, evidence, and a final sign-off.

Last reviewed: 2026-05-16, against a live audit of the codebase (931 passing tests) and the findings in CORE_TEST_READINESS.md.

0. Ground truth (read before planning anything)

These facts were verified this session and override older assumptions:

  1. Baseline is healthy. The unit/integration suite is 931 passed, 0 failed (~73 s, mocks Redis/AWS/S3 internally). There is no "27 failing tests" backlog. The single historical failure (test_generate_dispatches_to_gemini) was a test-helper bug and is already fixed.
  2. run_type is now wired (RESOLVED — was HIGH). config._ENV_MAP now maps run_type → ("RUN_TYPE", "run_type"). export run_type=local works; runner=local API path no longer 404s. Side effect: the env value must be a valid RunType (service|function|batch|local). Dockerfile.lambda previously set run_type=lambda (invalid) — fixed to function. The Lambda handler also pointed at a non-existent vaultdb.lambda module — fixed to vaultdb.core.function.handler (was a hard P0 blocker for the FUNCTION service type; see Phase 0).
  3. Auth-gate diverges across runners (MEDIUM). LOCAL send_task rejects a missing auth_token with ValueError; SERVICE / FUNCTION / BATCH do not — they dispatch and defer the gate to the worker via task headers. Pinned by tests/compute/test_runner_parity_matrix.py.
  4. TOCTOU is NOT protected (MEDIUM — TODO #7). verify_approval runs once before the RUNNING commit with no re-check inside that transaction. A revoke landing in that window is not caught. Pinned by tests/workflow/test_triple_gate_invariants.py. Any case asserting "execution aborts on concurrent revoke" will FAIL against current code — see §6, Case W4.
  5. Immutable approval archive does NOT exist (TODO #6). S3 Object-Lock archival of ApprovalRecord is unbuilt. Cases that assert it are deferred, not run.
  6. No Docker / LocalStack / MinIO / redis-server in the dev env. The automation path is mocked-by-default (moto + fakeredis, already installed and pinned). LocalStack/MinIO and real cloud are optional higher tiers requiring infra you provide — not the default.
  7. Artifact-under-test differs by phase. T0/T1 exercise the local working tree (core/src). The deployed images (infrastructure/docker/Dockerfile.{service,lambda,batch-*}) do pip install vaultdb.core from PyPI — so T2–T4 test the published package, NOT this session's local fixes, unless the images are rebuilt from a local wheel. Each phase below states its artifact; do not infer local-code coverage from a green T4.
  8. Shared-EFS uid mismatch across runners (P4/P5 risk). ECS service runs workloads as service (now pinned uid 1000); Batch runs as root; Lambda uses the Lambda sandbox user. All mount the same EFS access point for the DuckLake .ducklake commitlog. Cross-runner ownership conflicts are a corruption risk — tracked in INFRASTRUCTURE_REVIEW_PLAN.md §2.2; P4/P5 must assert commitlog read/write parity across runners, not just within one.
  9. Container deploy-gates (block P3/P5). From the docker/ review: Flower (5555) and Jupyter (8888) are ALB-exposed with auth that is absent/disabled by default — must be closed before any reachable deploy. Batch/Lambda images install only vaultdb.core, so they cannot run domain tasks (valuation.tasks.* → ModuleNotFoundError): P5 cannot test real workloads on Batch/Lambda until the domain modules are added to those images. Tracked in INFRASTRUCTURE_REVIEW_PLAN.md §1.8–1.11 (P0).

1. Test tiers (how "E2E" is layered)

Tier Backends Infra Speed Runs
T0 Unit/Integration in-proc + internal mocks none ~75 s every commit / CI
T1 Mocked E2E moto, fakeredis, real FastAPI none minutes every PR / CI
T2 Real Redis live Celery + Redis Redis URL (you) minutes pre-release
T3 Real S3 S3-backed DuckLake AWS creds + bucket (you) minutes pre-release
T4 Real AWS real Batch + Lambda deploy_infra.sh (you, $$) slow release gate only
T5 Manual UI browser OIDC/Dash human manual release gate only
T6 Production Readiness all of the above simulated failures & high load slow final pre-release gate

T0–T1 are permanent regression guards (automatable here, no infra). T2–T6 are release gates requiring infrastructure you provision.

2. The gated process

Phases run in order. Each has an entry gate (don't start until the prior gate is GREEN), an owner, and an exit gate. A failed exit gate stops the pipeline — no skipping ahead.

P0 Capability ─▶ P1 Baseline ─▶ P2 Mocked E2E ─▶ P3 Redis ─▶ P4 S3 ─▶ P5 AWS ─▶ P6 Manual UI ─▶ P7 Sign-off ─▶ P8 Prod Readiness
   (code)          (T0)           (T1)             (T2)        (T3)     (T4)       (T5)            (doc)            (T6)

Every phase appends evidence to a run log: docs/e2e-runs/<date>/ (commands, output tails, coverage deltas, screenshots).

Phase 2 — Mocked E2E (T1, no infra) (owner: Claude)

Entry: P1 green. Real FastAPI process + moto + fakeredis.

  • C-API.1 Boot python -m vaultdb.web; assert / 200 and tasks discovered.
  • C-API.2 Auth boundary: spider every router endpoint with no token → assert 401 (no data leak); invalid/expired/malformed token → 401.
  • C-RBAC.1 Non-admin DELETE /tasks/<id> → 403; admin → 200.
  • C-TED.LOCAL Sync task → immediate SUCCESS; raising task → traceback captured in result state.
  • C-TED.SERVICE fakeredis broker + eager mode: submit → poll PENDING→RUNNING→SUCCESS; revoke a sleeping task → REVOKED.
  • C-TED.BATCH / .FUNCTION moto: submit → assert exact AWS payload; AsyncResult.state polls mocked job lifecycle.
  • C-TED.PARITY Same logical task across all 4 runners → identical result contract (extends the existing parity matrix end-to-end).
  • C-WF.1 Separation of duties: submitter ≠ approver enforced (403).
  • C-WF.2 Triple-gate: missing approval / tampered HMAC / wrong key version / definition-hash mismatch → execution refused, zero step side effects.
  • C-WF.3 Idempotent retry: DONE steps skipped, resume at FAILED.
  • C-CRAWLER.1 Import does not instantiate paid LLM clients (lazy).
  • C-CRAWLER.2 Backend switch dispatches to the correct client class.

Exit gate: all green; this becomes a permanent CI suite (tests_e2e/, mocked tier, no infra required).

Phase 4 — Real S3 DuckLake (T3) (owner: Claude + you) — TODO #2

Entry: P3 green and you provide AWS creds + an S3 bucket.

export CATALOG_DATA_PATH=s3://<bucket>/data
  • D.1 Virtual-fork isolation: A and B fork main, edit the same row differently; neither sees the other's nor main's value.
  • D.2 Concurrent-writer lock: N threads write a delta simultaneously; serialized, no .ducklake corruption. (Note TODO #8: single-writer model — pin actual behavior if a distributed lock is absent.)

Exit gate: D.1–D.4 green against real S3.

Phase 8 — Production Readiness (T6, The "What if it breaks?" Tier) (owner: Claude + you)

Entry: P7 Go/No-Go sign-off complete. These tests validate the system under adversarial conditions.

  • PR.1 Chaos & Resilience: Simulate Redis disconnects (SERVICE_BROKER_URL temporary drops) and S3 eventual consistency. Assert no data loss and correct worker recovery. Simulate sudden worker death during a DuckLake commit.
  • PR.2 Load & Stress: Flood the FastAPI API with 10,000 tasks to test Rate Limiting (429) and Broker Saturation. Assert memory stability of the Celery worker and the DuckLake concurrent writer lock under extreme contention.
  • PR.3 Observability Audit: Assert distributed trace IDs propagate seamlessly across API -> Redis -> Celery -> Lambda. Assert that intentionally triggered errors with fake AWS/LLM keys correctly redact secrets from the log output.
  • PR.4 3rd-Party Circuit Breaking: Simulate 429 and 503 responses from OpenAI/Anthropic. Verify the BaseLLMAdvisor triggers exponential backoff or circuit breaks without crashing the parent workflow.
  • PR.5 Graceful Degradation: Send SIGTERM to the FastAPI web server and Celery workers during execution. Assert that active tasks finish or drain safely back to the queue.

Exit gate: All PR.1–PR.5 test cases written, executed, and passing. Evidence logged.

4. Deferred — pending features (DO NOT run as pass/fail)

These are tracked as known-gap pins until their TODO lands:

  • Immutable approval archive (S3 Object-Lock) — TODO #6.
  • TOCTOU abort on concurrent revoke — TODO #7. Current behavior (single pre-check, no in-transaction re-verify) is pinned, not asserted as correct.
  • Enforced single-writer / distributed lock for DuckLake — TODO #8.
  • Any P0 endpoint marked ABSENT (e.g. schema-publish, rate-limit 429, cross-schema 403) — removed from active cases until built.

5. Process rules

  • A failed exit gate halts the pipeline; fix forward, do not skip.
  • T0–T1 must stay green forever (regression guard); a red T0/T1 blocks all merges.
  • Phase 5 must be torn down (cost).
  • Every phase writes evidence to docs/e2e-runs/<date>/.
  • No E2E case may assert behavior for a feature P0 marked ABSENT/Deferred.
  • Re-run P0 whenever the API surface or config changes.
