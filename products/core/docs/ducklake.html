DuckLake Framework — Data Inheritance & Sandbox Model

DuckLake is a sandbox-first data inheritance framework built on DuckDB. It provides a low-level ORM and inherited reader to effortlessly manage overlapping production and user state without managing complex database servers or clusters.

Core Concepts

In financial or data-heavy applications, production data must remain pristine. Every user/analyst gets a Virtual Fork (a sandbox schema). The framework transparently overlays the sandbox on top of the main schema using vectorized SQL pushdown.

  1. Production Schema (main): The ground truth records.
  2. Sandbox Schema (sandbox_<role>): Delta records specific to a user/role.
  3. Merge & Override:
    • Same primary key? Sandbox overrides production.
    • Soft deleted in sandbox? Excluded from results.

Infrastructure & Efficiency

The framework eliminates the need for external database servers (like Nessie, Postgres, or Trino).

  • Storage: Apache Parquet files on S3.
  • Metadata: A single .ducklake file (DuckDB database) stored on S3.
  • Processing: Native DuckDB embedded in your application (FastAPI, Celery, Lambda).

Why DuckLake?

Typical Lakehouse architectures (Iceberg/Trino) require expensive, always-on query engines. DuckLake performs the compute logic natively in-memory within your existing application workers. When you call Model.get() or reader.read(), DuckDB fetches only the required Parquet bytes from S3 and performs the sandbox merge instantly.

The Model ORM

The heart of the system is the Model class, which maps Python objects to DuckLake tables.

from vaultdb.data import Model, Integer, Text, Float
from vaultdb.core import Application

class Trade(Model):
    __table_name__ = "trades"

    trade_id = Integer(primary_key=True)
    instrument = Text()
    quantity = Float()

# Connect to a catalog — all models resolve their catalog automatically
Application.connect(catalogs={"default": "prod.ducklake"})

Writing Data (Saving Deltas)

When you call save(), the object is committed to the user's sandbox schema.

# Creates an overriding delta in sandbox_analyst
trade = Trade(trade_id=1, instrument="AAPL", quantity=100.0)
trade.save()

# Deletes are soft-deletes added as tombstones to the sandbox
trade.delete()

Searching & Fetching Data

Queries dynamically merge main and sandbox data using optimized SQL pushdown.

# Get a single record by primary key (fully resolved)
my_trade = Trade.get(trade_id=1)

# Search dynamically by fields
apple_trades = Trade.search(instrument="AAPL")

Time-Series Models

Use TimeSeriesModel for historical data. It implicitly enforces a valuation_date primary key.

from datetime import date
from vaultdb.data import TimeSeriesModel, Text, Float

class Price(TimeSeriesModel):
    __table_name__ = "prices"
    instrument = Text(primary_key=True)
    price = Float()

# Fetch specific point in time natively
historical_price = Price.get(valuation_date=date(2023, 1, 1), instrument="AAPL")

Time-Travel (Point-In-Time Reproducibility)

DuckLake keeps a history of modifications. You can view the data exactly as it appeared at a previous timestamp or version.

from datetime import datetime, timezone

# What did the data look like yesterday?
yesterday = datetime(2023, 10, 15, tzinfo=timezone.utc)
old_data = Trade.search(timestamp=yesterday)

# Or query at a specific catalog version
version_data = Trade.search(version=10)

Publishing & Sharing Schema

The publish_schema method exports a schema-only .ducklake file — all table and column definitions, zero row data. This is how admin users and CI/CD pipelines distribute a canonical schema so that other environments can connect() and immediately have every table structure ready without calling sync_model() on each model.

from vaultdb.core import Application

# 1. Connect and create all tables (admin / build pipeline)
Application.connect(catalogs={"default": "s3://prod-bucket/prod.ducklake"})
Application.create_tables()

# 2. Publish schema-only catalog to a shared location
Application.publish_schema("s3://prod-bucket/schema/prod.ducklake")

# 3. Other environments download the schema file on connect()
#    and get all table structures for free — no sync_model() needed.
Application.connect(catalogs={"default": "s3://prod-bucket/schema/prod.ducklake"})

You can also call it directly on a DuckLakeCatalogManager:

catalog.publish_schema(
    dest_url="s3://shared-bucket/schema.ducklake",
    data_path="s3://shared-bucket/data",  # optional: override DATA_PATH
)

What the published file contains: - Every schema (namespace) in the catalog - Every table with full column definitions (name, type, NOT NULL) - The embedded DATA_PATH so consumers know where Parquet files live

What it does NOT contain: - No inlined row data - No Parquet data file references - No snapshot history

The output file is typically a few KB — small enough to commit to version control.

Supported destinations

Scheme Example
S3 s3://my-bucket/schema/prod.ducklake
Local path /shared/schema/prod.ducklake
File URI file:///shared/schema/prod.ducklake

In-Memory Object Mutations

For transient scenarios or stress-testing, use the MutationContext. This allows you to temporarily override values in memory without writing to the database.

from vaultdb.data.mutator import Mutator, MutationContext

mutator = Mutator(
    class_name="Trade",
    column_name="quantity",
    value_or_fn=lambda q: q * 2.0,
    keys={"trade_id": 1}
)

with MutationContext(mutator):
    # Within this block, trade 1 has double the quantity
    ...
# Upon exit, all changes are reverted.
